# 手沖咖啡紀錄平台 — 資料庫規格

> 本文件是三份規格中權限最高的一份。功能規格與介面規範若與本文件衝突，以本文件為準。
> 資料結構的錯誤需要 migration 才能修復，介面的錯誤重寫即可。因此本文件的所有約束都是硬性的。

---

## 0. 給實作者的硬性約束

**必須遵守，違反任何一條都視為實作錯誤：**

1. **不得自行新增本文件未列出的資料表或欄位。** 若實作過程中認為缺少某個欄位，停下來詢問，不要自行補上。
2. **不得建立 V2 功能的資料表。** 具體而言：不得建立 follows、likes、comments、notifications、或任何社群相關的表。
3. **不得將衍生值存成欄位。** 第 8 節列出所有衍生值，一律即時計算。
4. **所有使用者資料表都必須有 `user_id` 與 RLS policy。** 沒有 policy 的表視為未完成。
5. **`brew_steps` 必須是獨立資料表。** 不得改用 JSONB 陣列或文字欄位存放。這是本專案唯一不可妥協的結構決策。
6. **PostgreSQL ENUM 型別只用於第 3 節明確標示為「寫死」的欄位。** 其餘一律用查表（lookup table）＋外鍵。
7. **時間一律存 UTC**，時區轉換在前端處理。
8. **所有金額、重量、溫度使用 numeric 而非 float**，避免浮點誤差。

## 2. 資料表總覽

| 資料表 | 性質 | 說明 |
|---|---|---|
| `profiles` | 使用者 | 對應 auth.users |
| `equipment_catalog` | 系統 | 器材型錄，全域唯讀 |
| `user_equipment` | 使用者 | 使用者擁有的器材 |
| `beans` | 使用者 | 咖啡豆 |

| `flavor_tags` | 混合 | 風味標籤 |
| `countries` | 系統 | 產國，全域唯讀 |

**「混合」的定義**：同一張表同時存放系統資料（`user_id IS NULL`，所有人可讀）與使用者自建資料（僅本人可讀寫）。這類表的 RLS policy 寫法見第 6 節，是本專案最容易寫錯的地方。

### 3.2 equipment_catalog（系統表，全域唯讀）

器材型錄。**這張表存在的唯一目的是讓「刻度」這個數字可以被正確解讀。** 任何不服務這個目的的欄位都不要加。

```sql
create type equipment_type as enum ('grinder', 'dripper', 'filter', 'kettle', 'server');

create table equipment_catalog (
  id uuid primary key default gen_random_uuid(),
  type equipment_type not null,
  brand text not null,
  model text not null,
  variant text,                          -- 僅在「刻度意義改變」時建立，見下方說明
  grind_scale_min numeric,               -- 僅 grinder
  grind_scale_max numeric,               -- null = 無上限
  grind_scale_increment numeric,         -- null = 連續無段；否則為最小刻度間隔
  grind_scale_suggested_min numeric,     -- 選填，實用範圍下限
  grind_scale_suggested_max numeric,     -- 選填，實用範圍上限
  grind_scale_note text,                 -- 面板結構說明，顯示於輸入欄位旁
  sort_order int default 0,
  created_at timestamptz not null default now()
);

create index on equipment_catalog (type);
```

**刻度欄位的設計說明（重要，勿改回二分法）：**

磨豆機的刻度系統不是「有段／無段」的二分，而是**範圍**與**精度**兩個獨立維度。

`grind_scale_increment` 表達精度：

| 值 | 意義 | 例 |
|---|---|---|
| `1` | 只能停在整數格 | Comandante C40、1Zpresso 全系列、Baratza |
| `0.5` | 有半格定位 | 小富士 R440 |
| `0.1` | 可對齊到一位小數 | Mahlkönig EK43 |
| `null` | 連續無段，任意數值 | Niche Zero、Kinu M47、X54、Fellow Ode |

**`increment` 只在能乾淨表達時填入。** 若某機型的細分無法用有限小數表示（例如 Fellow Ode 每格再分三段），一律填 `null`，不要填 0.33——浮點驗證會誤判並擋住合法輸入。

`grind_scale_max` 為 `null` 代表無上限，前端不做上限檢查（Niche Zero 超過 50 仍可繼續旋轉）。

**「無段」不等於「沒有範圍」。** EK43 是 1–16 的連續刻度，仍應顯示範圍提示，只是不限制小數位數。前端的驗證邏輯：

```ts
// increment 為 null 時不檢查倍數，但範圍檢查照常
if (increment != null && value % increment !== 0) → 提示
if (min != null && value < min) → 提示
if (max != null && value > max) → 提示
```

**所有驗證都是提示，不阻擋儲存。** 使用者可能改裝、可能記錯、可能用型錄未涵蓋的方式讀數。擋住輸入的代價遠高於容忍異常值。

**這條的適用範圍是刻度欄位，不是全站通則。** 必填欄位（`beans.name`、`brews.dose`）該擋還是要擋——那是「沒有這個值這筆資料就沒有意義」，與「這個值看起來不太對」是兩回事。

`grind_scale_suggested_min` / `max` 用於在輸入欄位旁顯示實用範圍提示（例如「手沖常用 6–30」），服務的是不知道該從哪裡起步的新手。留空則不顯示。

**variant 的建立標準（實作時請嚴格遵守）：**

只有當「同一個刻度數字代表不同粗細」時才建立 variant。

- 應建立 variant：1Zpresso JX 與 JX-Pro（每格對應的微米數不同）；Fellow Ode Gen 1 與 Gen 2（刀盤不同）。
- 不應建立 variant：Comandante C40 MK3 與 MK4（刻度系統一致）；顏色、材質、限定版等商業區隔。

**改裝不屬於型錄。** 換刀盤、加裝 Red Clix 等個體改造，記錄在 `user_equipment.note`，不得在型錄中展開成新條目。

**無段磨豆機的處理**：`grind_scale_increment` 為 `null` 時，不檢查數值是否為特定倍數，但範圍檢查（min／max）照常進行。**不得禁止輸入，也不得阻擋儲存。** 這類機器的刻度雖無法跨機比較，對使用者本人仍是重要的記錄。

**完全無刻度標示的機型**（`min`、`max`、`increment` 三者皆為 `null`）：部分機型的調整轉盤上沒有任何數字或段數標示，例如楊家小飛馬 500N。此時前端不顯示任何範圍提示、不做任何驗證，僅顯示 `grind_scale_note` 的內容作為輔助說明，並允許使用者自由輸入任意數值或留空。

這類使用者通常會自行建立參考系統（在轉盤上做標記、以時鐘方向記錄、或計算旋轉圈數），系統不應預設任何格式，也不得因為填不出數字而阻擋紀錄儲存。

### 3.3 user_equipment

```sql
create table user_equipment (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users on delete cascade,
  catalog_id uuid references equipment_catalog on delete set null,
  type equipment_type not null,
  custom_name text,                   -- catalog_id 為空時必填
  is_default boolean not null default false,
  note text,                          -- 改裝、個體差異記錄於此
  created_at timestamptz not null default now(),
  constraint name_or_catalog check (catalog_id is not null or custom_name is not null)
);

create index on user_equipment (user_id, type);
create unique index on user_equipment (user_id, type) where is_default = true;
```

最後那個 partial unique index 確保每個類型只有一個預設器材。新增沖煮紀錄時，各類型的預設器材會自動帶入。

### 3.4 beans

```sql
create table beans (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users on delete cascade,
  name text not null,                          -- 唯一必填欄位
  photo_path text,                             -- Supabase Storage 路徑，列表首圖
  roaster text,                                -- 介面顯示為「咖啡店名」，見下方說明
  roast_date date,
  roast_level roast_level,
  country_id uuid references countries on delete set null,
  region text,                                 -- 自由文字，非查表，見下方說明
  processing_method_id uuid references processing_methods on delete set null,
  variety_id uuid references varieties on delete set null,
  official_notes text,                         -- 袋上印的風味描述
  is_finished boolean not null default false,  -- 已喝完
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create type roast_level as enum ('light', 'medium_light', 'medium', 'medium_dark', 'dark');

create index on beans (user_id, is_finished, created_at desc);
```

**除了 `name` 之外全部允許為空。** 這是首次使用流程能否成立的關鍵——使用者可以只拍一張豆袋照片、打一個豆名就開始記錄。實作時不得對其他欄位加上 not null 或前端必填驗證。

`roast_date` 為空時，養豆天數不顯示，不得阻擋儲存或顯示錯誤。

**`region` 是自由文字，不是查表。** 判斷依據：**封閉集合用查表，開放集合用自由文字。**

- 處理法、品種是封閉集合——條目有限、社群有共識，值得結構化。維持查表。
- 產區是開放集合——每個國家幾十個產區，往下還有莊園細分，本質上收不完。加上翻譯歧異（耶加雪菲／耶加雪夫／Yirgacheffe 都會出現在台灣豆袋上，沒有哪個是「對的」），用 `aliases` 維護會失控。

V1 的比較功能是同一支豆子的不同沖法，不是跨豆子的產區聚合，因此不需要結構化。未來若要做聚合，從使用者實際填過的文字正規化會比預先定義的清單更準確。

輸入行為：自由文字，不擋任何輸入。自動完成的建議來源是使用者自己填過的值（`select distinct region from beans`，RLS 已限定為本人），沒有歷史就沒有建議。

**不要改回查表。** 這個決定的成本在於未來的聚合分析，收益在於使用者現在就能把豆袋上的字原樣記下來，後者在 V1 更重要。

**`roaster` 的介面文案是「咖啡店名」。** 台灣沒有「烘焙商／烘豆商」這個說法，豆袋上印的是咖啡店名或自家烘焙店名。資料庫欄位名維持 `roaster` 不動，只有顯示文案不同。

**豆子表單沒有收合區，欄位全部可見**，順序如下：

豆袋照片 → `name` → `roaster` → `roast_date` → `roast_level` → `country_id` → `region` → `processing_method_id` → `variety_id` → `official_notes`

`roaster` 緊接在 `name` 之後：豆袋上的資訊結構是「某某店的某某豆」，店名是豆名的所屬關係，不是並列的另一個屬性。

處理法、品種、產區也留在可見範圍。台灣咖啡文化在豆袋上強調這三項，把它們收進第二層正是 Beanconqueror 被詬病的地方，也是本產品在地化差異的具體體現。

`is_finished` **不在表單裡**，由豆子詳情頁的開關負責（《02-功能規格》第 8 節）。

豆袋照片固定在表單**最上方**（理由見《02-功能規格》第 9 節）。

收合區機制保留給沖煮表單——只有那張表單長到需要分層。

### 3.5 brews（核心主體）

```sql
create table brews (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users on delete cascade,
  bean_id uuid not null references beans on delete cascade,
  brew_method_id uuid references brew_methods on delete set null,  -- 選填

  -- 參數
  dose numeric not null,                    -- 粉重 g
  water_temp int,                           -- 主水溫 °C
  grinder_id uuid references user_equipment on delete set null,
  grind_setting numeric,
  dripper_id uuid references user_equipment on delete set null,
  kettle_id uuid references user_equipment on delete set null,
  filter_id uuid references user_equipment on delete set null,     -- L2/V2
  server_id uuid references user_equipment on delete set null,     -- L2/V2
  total_time int,                           -- 總沖煮時間（秒），下壺滴完為準

  -- 進階（V2 才在介面露出，結構先建立）
  water_type text,
  water_tds numeric,
  room_temp int,
  humidity int,
  beverage_weight numeric,
  beverage_tds numeric,

  -- 品飲
  rating int,                               -- 1–5 星，可留空代表未評分
  is_favorite boolean not null default false,  -- 收藏／常沖，代表想再沖一次
  tasting_notes text,
  intensity jsonb,                          -- 見下方說明
  brew_photo_path text,                     -- L2/V2

  -- 系統
  brewed_at timestamptz not null default now(),
  copied_from_brew_id uuid references brews on delete set null,
  visibility visibility not null default 'private',
  form_duration_seconds int,                -- 產品指標，見第 9 節
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create type visibility as enum ('private', 'public');

create index on brews (user_id, brewed_at desc);
create index on brews (bean_id, brewed_at desc);
create index on brews (user_id, is_favorite) where is_favorite = true;
```

**`intensity` 的 JSONB 結構**（固定使用此格式）：

```json
{ "acidity": 3, "sweetness": 4, "body": 2, "bitterness": 1 }
```

四個 key 皆為 1–5 的整數，皆可省略。**刻意使用 JSONB 而非四個獨立欄位**，理由是評分維度是最可能被調整的一組定義，用欄位每次調整都需要 migration。

**`rating` 與 `is_favorite` 是兩個獨立欄位，介面上分開呈現，不得疊成一個複合元件。**

- `rating`：1–5 星，留空代表未評分，不強制填寫。點擊第 N 顆星讓 1 到 N 亮起；再次點擊目前已選中的那顆，整組清空回到未評分。這條與強度選擇器的清除規則一致。
- `is_favorite`：獨立的愛心，二元開關，代表「想再沖一次」。

兩者互不影響——可以只給星數不收藏，也可以只收藏不評分。

`rating` 有 `between 1 and 5` 的 check 約束。星等是封閉集合，超出範圍在定義上不存在，這與 §3.2「刻度驗證只是提示」是不同性質的東西。

**`visibility` 在第一版固定為 `private`，介面不得提供切換。** 欄位存在的目的是讓未來開放分享時不必修改核心權限邏輯。RLS policy 現在就要寫成考慮它的形式（見第 6 節）。

**`copied_from_brew_id` 是「自動 diff」功能的唯一資料來源。** 使用者透過複製建立新紀錄時填入來源 id。差異內容不另存欄位，即時比對計算（見第 8 節）。

### 3.6 brew_steps

```sql
create type step_type as enum ('bloom', 'pour', 'stir', 'wait');
create type pour_pattern as enum ('center', 'circle', 'spiral');

create table brew_steps (
  id uuid primary key default gen_random_uuid(),
  brew_id uuid not null references brews on delete cascade,
  user_id uuid not null references auth.users on delete cascade,
  step_index int not null,              -- 從 1 開始
  time_offset int not null,             -- 累積秒數，從沖煮開始起算
  cumulative_water numeric not null,    -- 累積水量 g（磅秤上的數字）
  step_type step_type not null default 'pour',
  temp_override int,                    -- V2 介面才露出；空值沿用 brews.water_temp
  pour_pattern pour_pattern,            -- V2 介面才露出
  note text,                            -- V2 介面才露出
  unique (brew_id, step_index)
);

create index on brew_steps (brew_id, step_index);
```

**這張表的三個關鍵設計，實作時不得更動：**

**一、儲存累積值，不是增量值。** 使用者在沖煮時看到的是磅秤上的累積水量（40 → 160 → 220 → 290），資料庫直接存這個數字。若需要顯示每段注了多少，由前端相減計算。

**二、悶蒸沒有獨立欄位。** 悶蒸就是 `step_index = 1` 且 `step_type = 'bloom'` 的那一筆。介面上會把它單獨呈現（見介面規範），但資料結構上它就是一般的一段。這讓未來新增任何段落型態都不需要改結構。

**三、輸入與儲存的單位不同。** 介面讓使用者填「停留秒數」（貼合實際體感），資料庫存「累積時間點」（可比較、可繪圖）。轉換在前端完成：`time_offset[n] = time_offset[n-1] + 停留秒數[n-1]`。**資料庫一律只認 `time_offset`。**

`temp_override` 用於後段降溫沖法。第一版介面不露出，結構先建立。

### 3.7 brew_methods（混合表）

```sql
create table brew_methods (
  id uuid primary key default gen_random_uuid(),
  user_id uuid references auth.users on delete cascade,  -- NULL = 系統內建
  name text not null,
  aliases text[] default '{}',          -- 供模糊比對，減少重複建立
  description text,
  default_ratio numeric,                -- 預設粉水比（水/粉）
  step_template jsonb,                  -- 分段模板，見下方
  sort_order int default 0,
  created_at timestamptz not null default now()
);

create index on brew_methods (user_id);
```

**`step_template` 結構**（比例制，依使用者實際粉重換算）：

```json
{
  "steps": [
    { "type": "bloom", "water_ratio": 0.10, "duration": 45 },
    { "type": "pour",  "water_ratio": 0.30, "duration": 45 },
    { "type": "pour",  "water_ratio": 0.20, "duration": 45 }
  ]
}
```

`water_ratio` 是該段注水量佔總水量的比例，全部相加須等於 1。`duration` 是該段的停留秒數。前端依使用者填的粉重與粉水比算出總水量，再換算成實際的累積水量與時間點寫入 `brew_steps`。

**手法只是模板來源與標籤，不是約束。** 帶入分段後使用者可以自由修改任何數值、增減段數，`brew_method_id` 仍然保留。系統不得在儲存時檢查實際分段是否符合模板。

### 3.8 查表型資料表

以下四張表結構相同，皆為「系統內建 ＋ 使用者自建」的混合表：

```sql
-- processing_methods（處理法）
-- varieties（品種）
-- flavor_tags（風味標籤）

create table processing_methods (
  id uuid primary key default gen_random_uuid(),
  user_id uuid references auth.users on delete cascade,  -- NULL = 系統內建
  name text not null,
  aliases text[] default '{}',
  sort_order int default 0,
  created_at timestamptz not null default now()
);
```

`flavor_tags` 額外有一個 `category text` 欄位（例如「酸質」「甜感」「口感」），用於分組顯示。

**countries 是純系統表**，沒有 `user_id`，全域唯讀，使用 ISO 3166-1 國碼建立，使用者不可新增。

```sql
create table countries (
  id uuid primary key default gen_random_uuid(),
  iso_code char(2) not null unique,
  name_zh text not null,
  name_en text not null,
  sort_order int default 0
);
```

### 3.9 brews 與 tasting 的合併決策

品飲欄位（`is_favorite`、`tasting_notes`、`intensity`、`brew_photo_path`）**直接放在 `brews` 表內，不另建 tasting 表**。

理由：使用情境是沖煮完一次填完，兩者是一對一且同時建立，拆表只會增加 join 成本與 null 判斷，沒有任何好處。

## 6. RLS Policy

**全部資料表都必須啟用 RLS。** 以下分三類寫法。

### 6.1 純使用者資料表

適用於 `profiles`、`user_equipment`、`beans`、`brew_steps`、`brew_flavor_tags`。

```sql
alter table beans enable row level security;

create policy "使用者讀取自己的豆子"
  on beans for select
  using (auth.uid() = user_id);

create policy "使用者新增自己的豆子"
  on beans for insert
  with check (auth.uid() = user_id);

create policy "使用者修改自己的豆子"
  on beans for update
  using (auth.uid() = user_id)
  with check (auth.uid() = user_id);

create policy "使用者刪除自己的豆子"
  on beans for delete
  using (auth.uid() = user_id);
```

### 6.2 brews（需考慮未來的 visibility）

第一版所有紀錄都是 private，但 policy **現在就要寫成考慮 visibility 的形式**，未來開放分享時不必修改核心權限邏輯：

```sql
alter table brews enable row level security;

create policy "讀取自己的或公開的沖煮紀錄"
  on brews for select
  using (auth.uid() = user_id or visibility = 'public');

create policy "只能新增自己的沖煮紀錄"
  on brews for insert
  with check (auth.uid() = user_id);

create policy "只能修改自己的沖煮紀錄"
  on brews for update
  using (auth.uid() = user_id)
  with check (auth.uid() = user_id);

create policy "只能刪除自己的沖煮紀錄"
  on brews for delete
  using (auth.uid() = user_id);
```

### 6.3 混合表（最容易寫錯，請特別注意）

適用於 `brew_methods`、`processing_methods`、`varieties`、`flavor_tags`。

規則是：**讀取時能讀到「系統項目 ＋ 自己建的」，寫入時只能寫自己的。**

```sql
alter table processing_methods enable row level security;

create policy "讀取系統項目與自己建立的項目"
  on processing_methods for select
  using (user_id is null or auth.uid() = user_id);

create policy "只能新增自己的項目"
  on processing_methods for insert
  with check (auth.uid() = user_id and user_id is not null);

create policy "只能修改自己建立的項目"
  on processing_methods for update
  using (auth.uid() = user_id and user_id is not null)
  with check (auth.uid() = user_id and user_id is not null);

create policy "只能刪除自己建立的項目"
  on processing_methods for delete
  using (auth.uid() = user_id and user_id is not null);
```

**insert policy 中的 `user_id is not null` 不可省略。** 少了這個條件，使用者可以建立 `user_id = NULL` 的項目，等同於偽造系統項目、讓所有使用者都看得到。這是本專案最可能出現的權限漏洞。

### 6.4 純系統表

`equipment_catalog`、`countries`：

```sql
alter table equipment_catalog enable row level security;

create policy "所有登入使用者可讀取"
  on equipment_catalog for select
  to authenticated
  using (true);
```

不建立 insert / update / delete policy。型錄維護透過 Supabase 後台或 service role 進行。

## 7. Storage

建立兩個 bucket，皆為 private：

| bucket | 用途 | 路徑格式 |
|---|---|---|
| `bean-photos` | 豆袋照片 | `{user_id}/{bean_id}.{ext}` |
| `brew-photos` | 沖煮照片（V2） | `{user_id}/{brew_id}.{ext}` |

Storage policy 依路徑第一層判斷擁有者：

```sql
create policy "使用者只能存取自己的豆袋照片"
  on storage.objects for all
  using (
    bucket_id = 'bean-photos'
    and (storage.foldername(name))[1] = auth.uid()::text
  );
```

上傳前在前端壓縮，長邊上限 1600px，品質 0.8，格式轉 WebP。單檔上限 2MB。

## 8. 衍生值（一律即時計算，不建欄位）

| 名稱 | 計算方式 | 空值處理 |
|---|---|---|
| 養豆天數 | `brewed_at` − `beans.roast_date` | `roast_date` 為空時不顯示 |
| 總水量 | `max(brew_steps.cumulative_water)` | 無分段時不顯示 |
| 粉水比 | 總水量 ÷ `dose` | 同上 |
| 每段增量水量 | `cumulative_water[n]` − `cumulative_water[n-1]` | 第一段即其本身 |
| 每段停留秒數 | `time_offset[n+1]` − `time_offset[n]` | 最後一段用 `total_time` − `time_offset[n]` |
| 萃取率 | `beverage_weight × beverage_tds ÷ dose` | 兩者任一為空則不顯示 |
| 相對上一版的差異 | 比對 `copied_from_brew_id` 指向的紀錄 | `copied_from_brew_id` 為空時不顯示 |

**差異計算的比對範圍**（僅這些欄位，其餘不比對）：

`dose`、`water_temp`、`grind_setting`、`grinder_id`、`dripper_id`、`kettle_id`、`brew_method_id`、`total_time`、以及 `brew_steps` 的整體結構（段數、各段累積水量、各段時間點）。

輸出格式建議：

```ts
type BrewDiff = {
  field: string        // 欄位名
  label: string        // 顯示名稱，如「研磨刻度」
  before: string       // 「22」
  after: string        // 「20」
}[]
```

**不要把差異結果存進資料庫。** 即時計算保證資料永遠一致；存下來則會在來源紀錄被編輯時失準。

## 9. 產品指標欄位

`brews.form_duration_seconds` 記錄「表單開啟到成功送出」的秒數。

前端在進入新增／複製流程時記下時間戳，送出時計算差值寫入。使用者不可見，不在任何介面顯示。

這個欄位的用途是驗證產品的核心假設（記錄時間能否壓到一兩分鐘內）。**不得省略，也不得讓使用者看到。**

Hario Buono、Fellow Stagg EKG、Brewista 溫控壺、Timemore Fish 系列、Kalita 鶴嘴、Takahiro、Bonavita。

### 10.4 處理法

水洗、日曬、蜜處理、紅蜜、黃蜜、黑蜜、白蜜、厭氧日曬、厭氧水洗、酒桶發酵、濕刨法、特殊處理法。

「特殊處理法」是刻意保留的 catch-all 選項，排在清單最後。處理法的創新速度快於型錄維護速度，這個選項讓使用者在遇到沒收錄的處理法時仍能完成記錄，而不是卡住或被迫自建。

### 10.5 沖煮手法（brew_methods）

**第一版只收錄 3–5 個社群共識明確、且經專案負責人確認參數正確的手法。** 寧可少，不可濫。候選：4:6 法（粕谷哲）、一刀流、三段式、Hoffmann V60 法。

每一個手法的 `step_template` 數值都必須由專案負責人提供並確認。實作者不得依網路資料或自身推測填寫。

`aliases` 欄位務必填滿常見別名（例如 4:6 法應包含「四六法」「46法」「Tetsu 4:6」「粕谷哲」），這是減少使用者重複自建的主要機制。

### 10.6 風味標籤

依 `category` 分組。這組標籤的設計目的不只是輸入輔助，更是給新手的詞彙教學——多數人不記錄風味，是因為缺乏描述詞彙而非懶惰。

建議分組：酸質（柑橘、莓果、青蘋果、發酵酸、檸檬）、甜感（蜂蜜、蔗糖、焦糖、紅棗、透明的甜）、口感（薄、圓潤、豆漿般的黏稠、絲滑、粗糙）、風味（堅果、可可、花香、茶感、香草、木質）、缺陷（澀、雜味、過萃的苦、水感）。

實際條目由專案負責人確認。
