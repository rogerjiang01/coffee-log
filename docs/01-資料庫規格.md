# 手沖咖啡紀錄平台 — 資料庫規格

> 本文件是三份規格中權限最高的一份。功能規格與介面規範若與本文件衝突，以本文件為準。
> 資料結構的錯誤需要 migration 才能修復，介面的錯誤重寫即可。因此本文件的所有約束都是硬性的。

---

## 0. 給實作者的硬性約束

**必須遵守，違反任何一條都視為實作錯誤：**

1. **不得自行新增本文件未列出的資料表或欄位。** 若實作過程中認為缺少某個欄位，停下來詢問，不要自行補上。
2. **不得建立 V2 功能的資料表。** 具體而言：不得建立 follows、likes、comments、notifications、或任何社群相關的表。
3. **不得將衍生值存成欄位。** 第 8 節列出所有衍生值，一律即時計算。
4. **所有使用者資料表都必須有 `user_id` 與 RLS policy。** 沒有 policy 的表視為未完成。
5. **`brew_steps` 必須是獨立資料表。** 不得改用 JSONB 陣列或文字欄位存放。這是本專案唯一不可妥協的結構決策。
6. **PostgreSQL ENUM 型別只用於第 3 節明確標示為「寫死」的欄位。** 其餘一律用查表（lookup table）＋外鍵。
7. **時間一律存 UTC**，時區轉換在前端處理。
8. **所有金額、重量、溫度使用 numeric 而非 float**，避免浮點誤差。

## 3. 資料表定義

### 3.1 profiles

```sql
create table profiles (
  id uuid primary key references auth.users on delete cascade,
  display_name text,
  sample_seeded boolean not null default false,  -- 是否已建立過範例資料（§13）
  record_step_times boolean not null default false,  -- 沖煮表單是否顯示分段時間欄位
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
```

第一版不需要頭像、簡介等欄位。使用者註冊時透過 trigger 自動建立對應的 profile。

**`record_step_times`：記錄分段時間的開關**（《02》§5 區塊三）。預設關閉。只決定沖煮表單上顯不顯示停水時間欄位，**不影響任何已記錄的時間**。

放在這裡而不是 `localStorage`：這是使用者對自己的宣告，屬於人，不屬於裝置。iOS 上 Safari 與加到主畫面的 app 是兩份各自的 `localStorage`，Safari 七天沒互動還可能被系統清掉——會打開這個開關的正是最在意時間的進階使用者，設定悄悄變回關閉，他的時間欄位就不見了，而他不一定察覺。

`not null default false`：偏好沒有「還沒決定」這個第三態。這不是使用者要填寫的欄位，不違反「必填只有三個」。

### 3.2 equipment_catalog（系統表，全域唯讀）

器材型錄。**這張表存在的唯一目的是讓「刻度」這個數字可以被正確解讀。** 任何不服務這個目的的欄位都不要加。

```sql
create type equipment_type as enum ('grinder', 'dripper', 'filter', 'kettle', 'server');

create table equipment_catalog (
  id uuid primary key default gen_random_uuid(),
  type equipment_type not null,
  brand text not null,
  model text not null,
  variant text,                          -- 僅在「刻度意義改變」時建立，見下方說明
  grind_scale_min numeric,               -- 僅 grinder
  grind_scale_max numeric,               -- null = 無上限
  grind_scale_increment numeric,         -- null = 連續無段；否則為最小刻度間隔
  grind_scale_suggested_min numeric,     -- 選填，實用範圍下限
  grind_scale_suggested_max numeric,     -- 選填，實用範圍上限
  grind_scale_note text,                 -- 面板結構說明，顯示於輸入欄位旁
  sort_order int default 0,
  created_at timestamptz not null default now()
);

create index on equipment_catalog (type);
```

**刻度欄位的設計說明（重要，勿改回二分法）：**

磨豆機的刻度系統不是「有段／無段」的二分，而是**範圍**與**精度**兩個獨立維度。

`grind_scale_increment` 表達精度：

| 值 | 意義 | 例 |
|---|---|---|
| `1` | 只能停在整數格 | Comandante C40、1Zpresso 全系列、Baratza |
| `0.5` | 有半格定位 | 小富士 R440 |
| `0.1` | 可對齊到一位小數 | Mahlkönig EK43 |
| `null` | 連續無段，任意數值 | Niche Zero、Kinu M47、X54、Fellow Ode |

**`increment` 只在能乾淨表達時填入。** 若某機型的細分無法用有限小數表示（例如 Fellow Ode 每格再分三段），一律填 `null`，不要填 0.33——浮點驗證會誤判並擋住合法輸入。

`grind_scale_max` 為 `null` 代表無上限，前端不做上限檢查（Niche Zero 超過 50 仍可繼續旋轉）。

**「無段」不等於「沒有範圍」。** EK43 是 1–16 的連續刻度，仍應顯示範圍提示，只是不限制小數位數。前端的驗證邏輯：

```ts
// increment 為 null 時不檢查倍數，但範圍檢查照常
if (increment != null && value % increment !== 0) → 提示
if (min != null && value < min) → 提示
if (max != null && value > max) → 提示
```

**所有驗證都是提示，不阻擋儲存。** 使用者可能改裝、可能記錯、可能用型錄未涵蓋的方式讀數。擋住輸入的代價遠高於容忍異常值。

**這條的適用範圍是刻度欄位，不是全站通則。** 必填欄位（`beans.name`、`brews.dose`）該擋還是要擋——那是「沒有這個值這筆資料就沒有意義」，與「這個值看起來不太對」是兩回事。

`grind_scale_suggested_min` / `max` 用於在輸入欄位旁顯示實用範圍提示（例如「手沖常用 6–30」），服務的是不知道該從哪裡起步的新手。留空則不顯示。

**variant 的建立標準（實作時請嚴格遵守）：**

只有當「同一個刻度數字代表不同粗細」時才建立 variant。

- 應建立 variant：1Zpresso JX 與 JX-Pro（每格對應的微米數不同）；Fellow Ode Gen 1 與 Gen 2（刀盤不同）。
- 不應建立 variant：Comandante C40 MK3 與 MK4（刻度系統一致）；顏色、材質、限定版等商業區隔。

**改裝不屬於型錄。** 換刀盤、加裝 Red Clix 等個體改造，記錄在 `user_equipment.note`，不得在型錄中展開成新條目。

**無刻度器材（濾杯、濾紙、手沖壺、分享壺）的收錄粒度：**

上面的 variant 標準是為磨豆機定的——它以「刻度意義是否改變」為界。**濾杯沒有刻度，這條界線在它身上不成立**，需要另一條。

**只收到「影響沖煮行為」的層級。** 結構、尺寸、流速這類會改變沖煮結果的差異才建立條目；材質、顏色、聯名版本一律不收。

| | 收 | 不收 |
|---|---|---|
| Kalita Wave | 155、185（兩種尺寸兩種流速） | 不鏽鋼／玻璃／陶瓷／美濃燒／波佐見燒／TSUBAME 等材質與聯名 |
| Hario V60 | 01、02、03（尺寸）；Switch 01／03（底部有閥門，可浸泡後再濾過，是不同沖煮方式） | 材質、顏色、限定版 |
| 星芒濾杯 | 1／2／3 代目（肋骨結構不同） | 材質 |

**理由是型錄的目的，不是產品目錄的完整性。** 型錄存在的唯一目的（見本節開頭）是讓刻度能被正確解讀；濾杯沒有刻度，它進型錄只是為了省打字與統一寫法。收全材質與聯名會讓濾杯型錄膨脹到三百筆以上，把「省打字」變成「在三百筆裡找一筆」——那時型錄反而是負擔。

**材質等個體差異記在 `user_equipment.note`**，與改裝走同一條路徑：那個欄位本來就是為個體差異設計的。

**寧可少收。** 型錄裡沒有的，使用者可以自建（`user_equipment.custom_name`），成本是打幾個字；型錄收太多，成本是每個人每次都要在長清單裡翻找。發現某個自建名稱反覆出現，再考慮升格成系統條目。

**無段磨豆機的處理**：`grind_scale_increment` 為 `null` 時，不檢查數值是否為特定倍數，但範圍檢查（min／max）照常進行。**不得禁止輸入，也不得阻擋儲存。** 這類機器的刻度雖無法跨機比較，對使用者本人仍是重要的記錄。

**完全無刻度標示的機型**（`min`、`max`、`increment` 三者皆為 `null`）：部分機型的調整轉盤上沒有任何數字或段數標示，例如楊家小飛馬 500N。此時前端不顯示任何範圍提示、不做任何驗證，僅顯示 `grind_scale_note` 的內容作為輔助說明，並允許使用者自由輸入任意數值或留空。

這類使用者通常會自行建立參考系統（在轉盤上做標記、以時鐘方向記錄、或計算旋轉圈數），系統不應預設任何格式，也不得因為填不出數字而阻擋紀錄儲存。

### 3.3 user_equipment

```sql
create table user_equipment (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users on delete cascade,
  catalog_id uuid references equipment_catalog on delete set null,
  type equipment_type not null,
  custom_name text,                   -- catalog_id 為空時必填
  is_default boolean not null default false,
  is_sample boolean not null default false,   -- 註冊時自動建立的範例（§13）
  note text,                          -- 改裝、個體差異記錄於此
  created_at timestamptz not null default now(),
  constraint name_or_catalog check (catalog_id is not null or custom_name is not null)
);

create index on user_equipment (user_id, type);
create unique index on user_equipment (user_id, type) where is_default = true;
```

最後那個 partial unique index 確保每個類型只有一個預設器材。新增沖煮紀錄時，各類型的預設器材會自動帶入。

### 3.4 beans

```sql
create table beans (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users on delete cascade,
  name text not null,                          -- 唯一必填欄位
  photo_path text,                             -- Supabase Storage 路徑，列表首圖
  roaster text,                                -- 介面顯示為「咖啡店名」，見下方說明
  roast_date date,
  roast_level roast_level,
  country_id uuid references countries on delete set null,
  region text,                                 -- 自由文字，非查表，見下方說明
  processing_method_id uuid references processing_methods on delete set null,
  variety_id uuid references varieties on delete set null,
  official_notes text,                         -- 袋上印的風味描述
  is_finished boolean not null default false,  -- 已喝完
  is_sample boolean not null default false,    -- 註冊時自動建立的範例（§13）
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create type roast_level as enum ('light', 'medium_light', 'medium', 'medium_dark', 'dark');

create index on beans (user_id, is_finished, created_at desc);
```

**除了 `name` 之外全部允許為空。** 這是首次使用流程能否成立的關鍵——使用者可以只拍一張豆袋照片、打一個豆名就開始記錄。實作時不得對其他欄位加上 not null 或前端必填驗證。

`roast_date` 為空時，養豆天數不顯示，不得阻擋儲存或顯示錯誤。

**`region` 是自由文字，不是查表。** 判斷依據：**封閉集合用查表，開放集合用自由文字。**

- 處理法、品種是封閉集合——條目有限、社群有共識，值得結構化。維持查表。
- 產區是開放集合——每個國家幾十個產區，往下還有莊園細分，本質上收不完。加上翻譯歧異（耶加雪菲／耶加雪夫／Yirgacheffe 都會出現在台灣豆袋上，沒有哪個是「對的」），用 `aliases` 維護會失控。

V1 的比較功能是同一支豆子的不同沖法，不是跨豆子的產區聚合，因此不需要結構化。未來若要做聚合，從使用者實際填過的文字正規化會比預先定義的清單更準確。

輸入行為：自由文字，不擋任何輸入。自動完成的建議來源是使用者自己填過的值（`select distinct region from beans`，RLS 已限定為本人），沒有歷史就沒有建議。

**不要改回查表。** 這個決定的成本在於未來的聚合分析，收益在於使用者現在就能把豆袋上的字原樣記下來，後者在 V1 更重要。

**`roaster` 的介面文案是「咖啡店名」。** 台灣沒有「烘焙商／烘豆商」這個說法，豆袋上印的是咖啡店名或自家烘焙店名。資料庫欄位名維持 `roaster` 不動，只有顯示文案不同。

**豆子表單沒有收合區，欄位全部可見**，順序如下：

豆袋照片 → `name` → `roaster` → `roast_date` → `roast_level` → `country_id` → `region` → `processing_method_id` → `variety_id` → `official_notes`

`roaster` 緊接在 `name` 之後：豆袋上的資訊結構是「某某店的某某豆」，店名是豆名的所屬關係，不是並列的另一個屬性。

處理法、品種、產區也留在可見範圍。台灣咖啡文化在豆袋上強調這三項，把它們收進第二層正是 Beanconqueror 被詬病的地方，也是本產品在地化差異的具體體現。

`is_finished` **不在表單裡**，由豆子詳情頁的開關負責（《02-功能規格》第 8 節）。

豆袋照片固定在表單**最上方**（理由見《02-功能規格》第 9 節）。

收合區機制保留給沖煮表單——只有那張表單長到需要分層。

### 3.5 brews（核心主體）

```sql
create table brews (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users on delete cascade,
  bean_id uuid not null references beans on delete cascade,
  brew_method_id uuid references brew_methods on delete set null,  -- 選填

  -- 參數
  dose numeric not null,                    -- 粉重 g
  water_temp int,                           -- 主水溫 °C
  grinder_id uuid references user_equipment on delete set null,
  grind_setting numeric,
  dripper_id uuid references user_equipment on delete set null,
  kettle_id uuid references user_equipment on delete set null,
  filter_id uuid references user_equipment on delete set null,     -- L2/V2
  server_id uuid references user_equipment on delete set null,     -- L2/V2
  total_time int,                           -- 沖煮時間（秒）

  -- 進階（V2 才在介面露出，結構先建立）
  water_type text,
  water_tds numeric,
  room_temp int,
  humidity int,
  beverage_weight numeric,
  beverage_tds numeric,

  -- 品飲
  rating int,                               -- 1–5 星，可留空代表未評分
  is_favorite boolean not null default false,  -- 收藏／常沖，代表想再沖一次
  is_sample boolean not null default false,    -- 註冊時自動建立的範例（§13）
  tasting_notes text,
  intensity jsonb,                          -- 見下方說明
  brew_photo_path text,                     -- L2/V2

  -- 系統
  brewed_at timestamptz not null default now(),  -- 沖煮日期（含時刻）。介面叫「沖煮日期」，「沖煮時間」是 total_time
  copied_from_brew_id uuid references brews on delete set null,
  visibility visibility not null default 'private',
  form_duration_seconds int,                -- 產品指標：記這一筆的互動秒數（閒置超過 60 秒的間隔不計），只在新增時寫入。見第 9 節
  params_duration_seconds int,              -- 產品指標：其中花在參數欄位上的秒數。見第 9 節
  tasting_duration_seconds int,             -- 產品指標：其中花在品飲欄位上的秒數。見第 9 節
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create type visibility as enum ('private', 'public');

create index on brews (user_id, brewed_at desc);
create index on brews (bean_id, brewed_at desc);
create index on brews (user_id, is_favorite) where is_favorite = true;
```

**`intensity` 的 JSONB 結構**（固定使用此格式）：

```json
{ "acidity": 3, "sweetness": 4, "body": 2, "bitterness": 1 }
```

四個 key 皆為 1–5 的整數，皆可省略。**刻意使用 JSONB 而非四個獨立欄位**，理由是評分維度是最可能被調整的一組定義，用欄位每次調整都需要 migration。

**`rating` 與 `is_favorite` 是兩個獨立欄位，介面上分開呈現，不得疊成一個複合元件。**

- `rating`：1–5 星，留空代表未評分，不強制填寫。點擊第 N 顆星讓 1 到 N 亮起；再次點擊目前已選中的那顆，整組清空回到未評分。這條與強度選擇器的清除規則一致。
- `is_favorite`：獨立的愛心，二元開關，代表「想再沖一次」。

兩者互不影響——可以只給星數不收藏，也可以只收藏不評分。

`rating` 有 `between 1 and 5` 的 check 約束。星等是封閉集合，超出範圍在定義上不存在，這與 §3.2「刻度驗證只是提示」是不同性質的東西。

**`visibility` 在第一版固定為 `private`，介面不得提供切換。** 欄位存在的目的是讓未來開放分享時不必修改核心權限邏輯。RLS policy 現在就要寫成考慮它的形式（見第 6 節）。

**分享一筆紀錄（第 14 節）不動 `visibility`。** 分享靠 `brew_shares` 加一個猜不到的代碼，讀取只走資料庫函式。把它做成 `visibility = 'public'` 會讓那筆紀錄對**所有登入使用者**可讀，範圍比「拿到連結的人」大得多——policy 裡的 `or visibility = 'public'` 是為了未來的公開瀏覽預留的，不是分享的實作方式。

**`copied_from_brew_id` 是「自動 diff」功能的唯一資料來源。** 使用者透過複製建立新紀錄時填入來源 id。差異內容不另存欄位，即時比對計算（見第 8 節）。

### 3.6 brew_steps

```sql
create type step_type as enum ('bloom', 'pour', 'stir', 'wait');
create type pour_pattern as enum ('center', 'circle', 'spiral');

create table brew_steps (
  id uuid primary key default gen_random_uuid(),
  brew_id uuid not null references brews on delete cascade,
  user_id uuid not null references auth.users on delete cascade,
  step_index int not null,              -- 從 1 開始
  hold_seconds int,                     -- 停水時間：注完到下一注之間。最後一段沒有下一注 → NULL
  cumulative_water numeric not null,    -- 累積水量 g（磅秤上的數字）
  step_type step_type not null default 'pour',
  temp_override int,                    -- V2 介面才露出；空值沿用 brews.water_temp
  pour_pattern pour_pattern,            -- V2 介面才露出
  note text,                            -- V2 介面才露出
  unique (brew_id, step_index)
);

create index on brew_steps (brew_id, step_index);
```

**這張表的三個關鍵設計，實作時不得更動：**

**一、儲存累積值，不是增量值。** 使用者在沖煮時看到的是磅秤上的累積水量（40 → 160 → 220 → 290），資料庫直接存這個數字。若需要顯示每段注了多少，由前端相減計算。

**二、悶蒸沒有獨立欄位。** 悶蒸就是 `step_index = 1` 且 `step_type = 'bloom'` 的那一筆。介面上它與其他段落在同一份清單，只有標題、不可刪除、不可標攪拌三處不同（見介面規範 §4.4），資料結構上它就是一般的一段。這讓未來新增任何段落型態都不需要改結構。

**三、停水時間原樣存，介面填什麼就存什麼。** `hold_seconds` 是「注完之後到下一注之前」的停水時間，**不含注水動作本身**，也不做任何換算。**不得再引入任何時間換算層。**

可為 NULL 是刻意的：沒記錄就是 NULL，最後一段永遠是 NULL（沒有下一注可以停，那段時間由 `total_time` 表達）。

舊版存的是累積時間點 `time_offset`（NOT NULL），「停留」被定義成「這段開始注水到下一段開始注水」的全部時間。那個定義要求使用者提供一個他不知道的數字——注水花了幾秒——**兩位實機測試者都填不出來**（「我以為是下沖的時間」；被告知定義之後仍然「不知道怎麼填」）。給水速率依器材與手法而異，還有行動誤差，無法預期；能預期、也真正被調整的是停水時間。而 NOT NULL 又讓「沒記錄」與「停 0 秒」共用同一個值，必須靠「全為 0 視為沒記錄」的變通；改成可空之後語意由資料直接表達。

之後若要記錄注水時長（例如用碼錶捕捉），加一個可空欄位即可——碼錶兩次按鍵之間的間隔就是停水時間，結構完全相容，既有資料不受影響。

`temp_override` 用於後段降溫沖法。第一版介面不露出，結構先建立。

### 3.7 brew_methods（混合表）

```sql
create table brew_methods (
  id uuid primary key default gen_random_uuid(),
  user_id uuid references auth.users on delete cascade,  -- NULL = 系統內建
  name text not null,
  aliases text[] default '{}',          -- 供模糊比對，減少重複建立
  description text,
  default_ratio numeric,                -- 預設粉水比（水/粉）
  step_template jsonb,                  -- 分段模板，見下方
  sort_order int default 0,
  created_at timestamptz not null default now()
);

create index on brew_methods (user_id);
```

**`step_template` 結構**（依使用者實際粉重換算）：

```json
{
  "steps": [
    { "type": "bloom", "basis": "dose",      "factor": 2,   "duration": 30, "note": "讓粉床完全濕透" },
    { "type": "pour",  "basis": "remaining", "factor": 0.6, "duration": 30 },
    { "type": "pour",  "basis": "remaining", "factor": 0.4, "duration": null }
  ]
}
```

| 欄位 | 說明 |
|---|---|
| `type` | 對應 `brew_steps.step_type` |
| `basis` | 水量基準，見下 |
| `factor` | 依 `basis` 解讀的係數 |
| `duration` | 該段的停水時間（對應 `brew_steps.hold_seconds`）。最後一段沒有下一注，為 `null` |
| `note` | 選填，對應 `brew_steps.note` |

**`basis` 的三種值：**

| 值 | 水量 |
|---|---|
| `dose` | 粉重 × `factor` |
| `total` | 總水量 × `factor` |
| `remaining` | 該組基準 × `factor`。**基準在該組第一段時算一次**（總水量 − 當時已分配），之後固定不變 |

總水量由粉重與 `default_ratio` 算出。`type` 與 `note` 在帶入時要一併寫進 `brew_steps`。

**基準由每個模板自己宣告，不得由系統統一決定。** 判斷依據：

- **悶蒸是物理需求，綁粉重。** 它要讓粉床完全濕透、排出二氧化碳，需求量由粉重決定，與總水量無關。若改用比例，20g 粉配 1:12（總水 240ml）時悶蒸 10% 只有 24ml，僅粉重的 1.2 倍，粉根本濕不透——而 1:12 與 1:20 都是真實會出現的粉水比，不是極端假設。
- **但也不能統一改成綁粉重。** 4:6 法的第一注不是悶蒸，它是「前 40% 分兩注」這個結構的一部分，改成粉重倍數會破壞 4:6 的核心機制。

兩種需求本質不同，所以基準必須由模板宣告。

**計算規則：**

1. 每段四捨五入到整數 ml。
2. **最後一段用「總水量 − 前面所有段的累計」**，不用公式計算，確保總和精確等於總水量，避免小數誤差累積。
3. 邊界保護：若 `dose × factor > 總水量 × 0.5`，代表粉水比極端到悶蒸會吃掉一半的水。此時不採用該數值，改按總水量比例計算，並在介面顯示提示。
4. 同一組 `remaining` 的 `factor` 總和必須為 1；`total` 的 `factor` 總和（不含 `dose` 段）也必須為 1。寫入 seed 前須驗證。

**`remaining` 的基準為什麼固定而不是每段重算。** 若每段都用「當下剩餘」重新計算，四個 `0.25` 會得到 60／45／34／101 這種遞減後暴增的分配——最後一注佔了悶蒸後水量的 42%，不是 25%。這樣「總和為 1」不產生任何保證，五段式的「等分四注」、肥尾的「高頻補水小水量」也全部對不上。基準固定時，四個 `0.25` 就是實實在在的四等分。

**手法只是模板來源與標籤，不是約束。** 帶入分段後使用者可以自由修改任何數值、增減段數，`brew_method_id` 仍然保留。系統不得在儲存時檢查實際分段是否符合模板。

## 6. RLS Policy

**全部資料表都必須啟用 RLS。** 以下分三類寫法。

### 6.1 純使用者資料表

適用於 `profiles`、`user_equipment`、`beans`、`brew_steps`、`brew_flavor_tags`。

```sql
alter table beans enable row level security;

create policy "使用者讀取自己的豆子"
  on beans for select
  using (auth.uid() = user_id);

create policy "使用者新增自己的豆子"
  on beans for insert
  with check (auth.uid() = user_id);

create policy "使用者修改自己的豆子"
  on beans for update
  using (auth.uid() = user_id)
  with check (auth.uid() = user_id);

create policy "使用者刪除自己的豆子"
  on beans for delete
  using (auth.uid() = user_id);
```

### 6.2 brews（需考慮未來的 visibility）

第一版所有紀錄都是 private，但 policy **現在就要寫成考慮 visibility 的形式**，未來開放分享時不必修改核心權限邏輯：

```sql
alter table brews enable row level security;

create policy "讀取自己的或公開的沖煮紀錄"
  on brews for select
  using (auth.uid() = user_id or visibility = 'public');

create policy "只能新增自己的沖煮紀錄"
  on brews for insert
  with check (auth.uid() = user_id);

create policy "只能修改自己的沖煮紀錄"
  on brews for update
  using (auth.uid() = user_id)
  with check (auth.uid() = user_id);

create policy "只能刪除自己的沖煮紀錄"
  on brews for delete
  using (auth.uid() = user_id);
```

### 6.3 混合表（最容易寫錯，請特別注意）

適用於 `brew_methods`、`processing_methods`、`varieties`、`flavor_tags`。

規則是：**讀取時能讀到「系統項目 ＋ 自己建的」，寫入時只能寫自己的。**

```sql
alter table processing_methods enable row level security;

create policy "讀取系統項目與自己建立的項目"
  on processing_methods for select
  using (user_id is null or auth.uid() = user_id);

create policy "只能新增自己的項目"
  on processing_methods for insert
  with check (auth.uid() = user_id and user_id is not null);

create policy "只能修改自己建立的項目"
  on processing_methods for update
  using (auth.uid() = user_id and user_id is not null)
  with check (auth.uid() = user_id and user_id is not null);

create policy "只能刪除自己建立的項目"
  on processing_methods for delete
  using (auth.uid() = user_id and user_id is not null);
```

**insert policy 中的 `user_id is not null` 不可省略。** 少了這個條件，使用者可以建立 `user_id = NULL` 的項目，等同於偽造系統項目、讓所有使用者都看得到。這是本專案最可能出現的權限漏洞。

### 6.4 純系統表

`equipment_catalog`、`countries`：

```sql
alter table equipment_catalog enable row level security;

create policy "所有登入使用者可讀取"
  on equipment_catalog for select
  to authenticated
  using (true);
```

不建立 insert / update / delete policy。型錄維護透過 Supabase 後台或 service role 進行。

### 6.5 完全不開放給角色的表

`brew_shares`、`brew_share_events`（§14）走的是第三種模式：**不給角色寫入的 table privilege，寫入一律經由 `security definer` 函式。** 匿名讀取也不開表，只開一支只回傳白名單欄位的函式。設計與理由見第 14 節。

## 7. Storage

建立兩個 bucket，皆為 private：

| bucket | 用途 | 路徑格式 |
|---|---|---|
| `bean-photos` | 豆袋照片 | `{user_id}/{bean_id}.{ext}` |
| `brew-photos` | 沖煮照片（V2） | `{user_id}/{brew_id}.{ext}` |

Storage policy 依路徑第一層判斷擁有者：

```sql
create policy "使用者只能存取自己的豆袋照片"
  on storage.objects for all
  using (
    bucket_id = 'bean-photos'
    and (storage.foldername(name))[1] = auth.uid()::text
  );
```

上傳前在前端壓縮，長邊上限 1600px，品質 0.8，格式轉 WebP。單檔上限 2MB。

**分享頁不得讓前端自己去要簽名網址。** 兩個 bucket 都是 private，未登入的人沒有 Storage 權限，policy 也是以 `auth.uid()` 判斷擁有者。第一版的分享頁沒有任何照片（紀錄詳情頁本來就不顯示照片，`brews.brew_photo_path` 是 V2），所以讀取函式目前不回傳照片；**之後要顯示時，由 `get_shared_brew` 產生有時效的網址，每次開啟重新產生，不快取、不寫進資料表**（§14.5）。

## 8. 衍生值（一律即時計算，不建欄位）

| 名稱 | 計算方式 | 空值處理 |
|---|---|---|
| 養豆天數 | `brewed_at` − `beans.roast_date` | `roast_date` 為空時不顯示 |
| 總水量 | `max(brew_steps.cumulative_water)` | 無分段時不顯示 |
| 粉水比 | 總水量 ÷ `dose` | 同上 |
| 每段增量水量 | `cumulative_water[n]` − `cumulative_water[n-1]` | 第一段即其本身 |
| 萃取率 | `beverage_weight × beverage_tds ÷ dose` | 兩者任一為空則不顯示 |
| 相對上一版的差異 | 比對 `copied_from_brew_id` 指向的紀錄 | `copied_from_brew_id` 為空時不顯示 |

**每段停水時間不是衍生值。** 它直接存在 `brew_steps.hold_seconds`（§3.6），介面填什麼就存什麼，**不從 `total_time` 或任何欄位反推**。沒記錄就是 NULL；最後一段永遠是 NULL。

判斷一筆紀錄有沒有記錄分段時間，一律走 `hasStepTiming()`（`utils/brewSteps.ts`）：全部為 NULL 就是沒記錄，不在各處自己寫條件。差異計算沿用同一個判斷——兩邊都沒記錄時不比對「各段停水時間」，只有一邊有記錄時另一邊顯示「沒記錄」。

**差異計算的比對範圍**（僅這些欄位，其餘不比對）：

`dose`、`water_temp`、`grind_setting`、`grinder_id`、`dripper_id`、`kettle_id`、`brew_method_id`、`total_time`、以及 `brew_steps` 的整體結構（段數、各段累積水量、各段停水時間）。

輸出格式建議：

```ts
type BrewDiff = {
  field: string        // 欄位名
  label: string        // 顯示名稱，如「研磨刻度」
  before: string       // 「22」
  after: string        // 「20」
}[]
```

**不要把差異結果存進資料庫。** 即時計算保證資料永遠一致；存下來則會在來源紀錄被編輯時失準。

## 9. 產品指標欄位

`brews.form_duration_seconds` 記錄**記這一筆實際互動了多少秒**。

**定義**：從表單開啟起，累計相鄰兩次互動之間的間隔，**超過 60 秒的間隔不計入**。「互動」包含輸入、選擇、點擊、捲動；表單開啟與按下送出也各算一次。例：填 30 秒 → 放著 40 分鐘 → 再填 20 秒，記 50 秒，不是 2450 秒。門檻與理由見 `utils/interactionTime.ts` 的 `IDLE_GAP_MS`：要大到涵蓋「想一下再填」，小到排除「開著表單去沖咖啡」。

**只在新增流程寫入**（含從空白新增與複製）。編輯既有紀錄不覆蓋、也不累加：要量的是「記一筆要多久」，不是「總共花多少時間維護這筆」。

使用者不可見，不在任何介面顯示。

**舊定義與歷史資料**：2026-09-17 之前是「表單開啟到成功送出」的秒數，包含開著表單去做別的事的時間，實測出現 3128 秒、2620 秒這種值。**2026-09-17 之前的資料用的是舊定義（含閒置時間），不可與之後的資料混合統計。** 那些資料不修改，留作歷史。

這個欄位的用途是驗證產品的核心假設（記錄時間能否壓到一兩分鐘內）。**不得省略，也不得讓使用者看到。**

### 9.1 參數與品飲分開計時

`form_duration_seconds` 一個數字回答不了那個假設：它混了參數與品飲，而**品飲本來就慢**——強度要想、風味詞要挑、心得要寫。要判斷「參數記錄一兩分鐘內完成」有沒有達成，得把兩段分開。

`brews.params_duration_seconds` 與 `brews.tasting_duration_seconds` 記錄其中各自的秒數。

| 區段 | 欄位 |
|---|---|
| 參數 | 豆子、器材（磨豆機、濾杯、手沖壺、濾紙、分享壺）、粉重、水溫、研磨刻度、沖煮手法、分段注水、沖煮時間 |
| 品飲 | 強度、風味標籤、心得筆記、星等評分、收藏 |
| 兩者都不算 | 沖煮日期、照片。只計入總耗時 |

粉水比與養豆天數是衍生值，沒有欄位可以操作，不歸任何一段。

**分配方式**：依使用者當下操作（聚焦或輸入）所在的區段。每一段互動間隔算給**區間開始時**的那一段——在粉重打完字、過五秒點進心得筆記，那五秒算參數，因為那五秒他還在看參數。判斷不出區段的互動（捲動、teleport 到 `<body>` 的浮層、送出按鈕）沿用上一次的區段：浮層的 DOM 不在任何一段裡，但打開它的觸發元素在。

**閒置與背景沿用 `form_duration_seconds` 的規則**，兩者用的是同一個時鐘、同一批間隔，不是另一套量法。因此 `params + tasting ≤ form_duration_seconds`，差額是「兩者都不算」那些欄位。照片裁切可能花很久，算進參數會讓數字失真，所以它落在差額裡。

**只在新增流程寫入**，編輯既有紀錄不覆蓋也不累加，與 `form_duration_seconds` 一致。

**既有紀錄不回填，維持 NULL。** 那些紀錄沒有留下任何可以還原區段的痕跡，用估算值回填會產生看起來像量測結果的假資料。NULL 的意思是「這筆沒有分段資料」，不是 0。

**`form_duration_seconds` 的算法不因此改變。** 新舊資料已經因為 2026-09-17 的定義變更斷過一次，不能再斷第二次。

### 9.2 brew_save_events：每次儲存都記一筆

`brews` 上的三個欄位只在建立時寫入，而兩種真實的使用方式會因此被截斷：

1. **每填一點就按儲存的人**，只有第一次儲存前的時間被記到
2. **沖之前先存、沖完回來補填的人**，補填的那段完全沒被記到

兩種截斷都讓耗時**偏短**，剛好讓「參數記錄一兩分鐘內完成」看起來達成了。量測誤差偏向我們希望看到的結論，那比沒有量測更糟。

**原則：原始資料全部記下來，「怎樣算一次記錄」留到查詢時再定義。** 分段時間那次的教訓是，定義寫死在儲存端，之後改定義就要搬資料，舊資料也會斷掉。所以這張表只記「哪一筆、從哪個入口、花了多少秒」；「同一筆紀錄在 N 分鐘內的多次儲存算同一次記錄」是 `supabase/queries/記錄耗時盤點.sql` 的事，改 N 不必動資料。

```sql
create table brew_save_events (
  id uuid primary key default gen_random_uuid(),
  brew_id uuid not null references brews on delete cascade,
  user_id uuid not null references auth.users on delete cascade,
  entry text not null check (entry in ('blank', 'bean', 'copy', 'edit')),
  params_seconds int not null,
  tasting_seconds int not null,
  total_seconds int not null,
  saved_at timestamptz not null default now()
);
```

**`entry` 沿用暫存 key 的分法**（`utils/draft.ts` 的 `brewSaveEntry`）：`blank`＝空白新增、`bean`＝指定豆子、`copy`＝複製、`edit`＝編輯既有紀錄。入口的定義已經在暫存 key 上了，另外定一套遲早會分岔。認不出入口時**不寫入**——歸錯的一列比缺一列難處理。

**秒數的算法與 §9、§9.1 完全相同**：同一個計時器、同一個 60 秒門檻、同一套區段歸屬。差別只在「每次儲存都寫一列」。

**RLS 只有 insert policy。** 這是單向的量測紀錄，介面不讀它，盤點在 SQL Editor 做；少一個 policy 就少一個寫錯的機會。刪除由 `brew_id` 的 `on delete cascade` 處理。`with check` 除了比對 `user_id`，還要確認那筆 `brew_id` 是自己的——只比對 `user_id` 的話，A 可以帶自己的 id 對 B 的紀錄寫入，汙染的是 B 的統計。**table privilege 只給 `insert`**：權限層與 policy 一致比較好查問題，代價是用戶端 `insert` 之後不得接 `.select()`。

**寫入時機**：沖煮紀錄儲存成功之後。失敗的儲存不該產生一列，那次的時間會被下一次成功的儲存一起帶進去。**寫入失敗不影響儲存結果**：不顯示錯誤、不重試，只在開發模式印出。使用者存不了紀錄的代價遠高於少一列統計。

**`brews` 上的三個欄位維持原樣**：建立時照舊寫入，編輯時照舊不更新。它們與這張表是兩套資料，不互相覆蓋——改了就是新舊資料再斷一次。

**既有紀錄不回填。** 改版前的資料只存在 `brews` 的三個欄位。

## 13. 新使用者的範例資料

第一次進來看到一片空白，使用者得先建豆子、建器材、填沖煮、填品飲才看得到任何東西——而首次使用正是風險最高的一段（《02》§9）。範例讓他先看到「記完之後長什麼樣子」，再決定要不要自己記一筆。

**範圍**：只有這項功能上線之後註冊的人才有。**既有使用者不補**——補了等於在別人已經在用的資料裡塞三筆他沒建立的東西。

### 13.1 內容

每位新使用者建立三筆，全部歸屬於他自己：

| 資料 | 內容 | 為什麼 |
|---|---|---|
| 磨豆機 | 型錄裡刻度四欄與建議範圍都齊全的機型，`is_default = false` | 範例紀錄的刻度要能示範「刻度跟著磨豆機型號解讀」。不設常用：常用會自動帶入每一張新表單，那是使用者自己的選擇 |
| 豆子 | 烘焙日期為註冊日往前數天，產國、產區、處理法、品種、袋上風味都填好 | 養豆天數要看起來合理，詳情頁的每一格也才不是空的 |
| 沖煮紀錄 | 用上面的豆子與磨豆機，套一個內建手法帶出分段注水，填好強度、風味標籤、評分與心得 | 紀錄詳情、比較表、品飲區三個地方都要有東西可看 |

**實際的文字與數值集中在建立函式的 `declare` 區塊**（`supabase/migrations/*_sample_data.sql`），改內容只改那裡。分段的水量與停水秒數不是另外編的數字，是把該手法的模板套範例粉重算出來的結果（`utils/brewSteps.ts` 的 `stepsFromTemplate`），`tests/db/sample-data.test.mjs` 會重算一次比對。

**心得筆記那一句是唯一的說明文字**：說明這是範例、可以直接刪除，並指出可以從豆子頁試一次複製。不做教學浮層、導覽步驟或任何其他說明文字。

### 13.2 範例標記

`beans`、`user_equipment`、`brews` 各有一個 `is_sample boolean not null default false`。

**標記只做兩件事：顯示「範例」標籤（《03》§4.12）、從統計裡排除。** 編輯、刪除、複製的行為與一般資料完全相同——範例就是使用者自己的資料。

**標記不因編輯而消失。** 「改過就變成真的」使用者猜不到：改了豆名算不算？改了刻度算不算？規則要能預測，所以標記只跟著資料本身走。

**從範例紀錄複製出來的新紀錄不帶標記**——那一杯是使用者自己沖的。複製流程是照表單上的值新建一筆，不複製這個欄位。

**統計一律排除範例。** V1 唯一的統計出口是 `supabase/queries/`，那裡每一段都加了 `is_sample = false`（含經由 `brew_id` 過濾儲存事件的那幾段——使用者編輯範例並儲存時也會寫下儲存事件）。首頁豆子卡片上的「沖過幾次」「收藏幾次」不算統計，那是這支豆子自己的計數，範例豆子的卡片照常顯示它自己的範例紀錄。

**範例紀錄本身不寫 `brew_save_events`，三個耗時欄位也留空**：那些記的是「使用者按了儲存花了多久」，範例不是使用者記的。

### 13.3 建立時機

掛在註冊的 trigger 上（`handle_new_user`，§3.1）：profile 建完之後呼叫建立函式。

**範例建立失敗時，註冊必須照樣成功。** 呼叫包在自己的例外區塊裡，失敗只記 `warning` 不往上拋——註冊失敗的代價是使用者根本進不來，遠高於少三筆範例。profile 的 insert 不包在裡面，那是註冊本身的一部分。

**每位使用者只建立一次**，依據是 `profiles.sample_seeded`（建立成功才設為 true）。判斷的是「建立過沒有」而不是「現在還有沒有」：使用者刪掉範例之後不會再冒出來。既有使用者的 `sample_seeded` 是 false，但沒有任何流程會替他建立——唯一的呼叫點是註冊 trigger。

## 14. 分享沖煮紀錄

使用者把一筆沖煮紀錄變成一個連結傳給朋友。朋友不論有沒有登入都能看，只能看、不能改；看的人不留副本，要再看就再點一次連結。流程與畫面見《02》§7.1、§7.2。

**這一節的核心約束：匿名的人碰不到任何一張表。** 讀取只有一個入口，是一支只回傳白名單欄位的函式。

**第一版沒有「停止分享」**（2026-09-23 決定，《02》§11）。要讓一個連結失效，方式是刪除那筆紀錄。`revoked_at` 欄位保留，日後加回停止分享時不必改表，**但這一版沒有任何寫入它的路徑**：沒有函式寫它，也沒有任何角色有 `update` 權限。

### 14.1 兩張表

```sql
create table brew_shares (
  id uuid primary key default gen_random_uuid(),
  brew_id uuid not null references brews on delete cascade,
  user_id uuid not null references auth.users on delete cascade,
  code text not null unique check (code ~ '^[A-Za-z0-9_-]{22}$'),
  include_notes boolean not null default false,
  revoked_at timestamptz,                        -- null ＝ 生效中。第一版沒有寫入路徑，一律是 null
  created_at timestamptz not null default now()
);

-- 一筆紀錄同時只能有一個生效中的連結。
-- 「重複分享沿用同一個連結」不是靠程式記得去查，是靠這條索引保證
create unique index brew_shares_live on brew_shares (brew_id) where revoked_at is null;
create index on brew_shares (user_id);
```

- `code` 是網址上那一段：128 bits 的亂數轉 base64url，22 個字元。**不得由 `id`、`brew_id` 或任何已知值推導出來。**
- `revoked_at` 與部分唯一索引是為了日後的停止分享預留的：到時候停止分享**不刪除列**，只填 `revoked_at`——列留著，舊代碼才永久失效；刪掉的話同一個代碼理論上可以再被產生出來，掛在它底下的事件也會一起 cascade 掉。
- 第一版一筆紀錄至多一列。

```sql
create table brew_share_events (
  id uuid primary key default gen_random_uuid(),
  share_id uuid not null references brew_shares on delete cascade,
  event text not null check (event in ('create', 'toggle_notes', 'open')),
  include_notes boolean,                         -- create / toggle_notes：當下的狀態
  viewer text check (viewer in ('anon', 'member', 'owner')),  -- open：開啟者的身分
  occurred_at timestamptz not null default now()
);

create index on brew_share_events (share_id, occurred_at);
```

**原則與 §9.2 相同：記原始事件，怎麼解讀留到查詢時。** 這張表不回答「這個連結被看了幾次」，它只記「什麼時候發生了什麼」。

| `event` | `include_notes` | `viewer` |
|---|---|---|
| `create` | 建立時的狀態 | NULL |
| `toggle_notes` | **改之後**的狀態 | NULL |
| `open` | NULL | `anon` 未登入／`member` 已登入但不是分享者／`owner` 分享者本人 |

`event` 的 check 不含 `revoke`：沒有寫入路徑的值不先開。日後加回停止分享時，改 check constraint 是一行 `alter`。

**本人的開啟不得混進朋友的開啟次數。** 分享者點自己的連結是常態（《02》§7.2 的理由），不分開記的話，開啟數最大的貢獻者會是分享者自己。查詢時一律 `viewer <> 'owner'`。

**失效的開啟不記事件**：代碼不存在、紀錄已刪除，兩種情況都沒有可以掛的 `share_id`。想知道有多少人點到死連結的話，那要另一張表，第一版不做。

### 14.2 讀取：只有一支函式，不開表

```sql
create function public.get_shared_brew(share_code text)
returns jsonb
language plpgsql
security definer
set search_path = ''
as $$ … $$;

revoke all on function public.get_shared_brew(text) from public, anon, authenticated;
grant execute on function public.get_shared_brew(text) to anon, authenticated;
```

- `anon` 對 `brews`、`brew_steps`、`beans`、`user_equipment`、`brew_flavor_tags`、`brew_shares`、`brew_share_events` **一律沒有 table privilege**。不是靠 policy 擋，是連表都碰不到。
- **函式除了 `share_code` 不吃任何參數。** 特別是不吃 `brew_id`——吃了它就變成一個可以指定任意紀錄的後門。
- `security definer` 會繞過 RLS，所以**函式必須自己做完所有檢查**。`set search_path = ''` 表示裡面每一個名字都要加 schema。
- 函式會寫開啟事件，所以是 `volatile`（預設值），不能標成 `stable`。

**白名單 ＝ 分享頁實際顯示的欄位，一欄都不能多**（2026-09-23 決定）。函式回傳了畫面上沒顯示的欄位，一般人看不到，但任何人打開瀏覽器的開發者工具就看得到——等於不知不覺多公開了資料。所以

- 要在分享頁多顯示一個欄位，先改這張表，再改函式，最後改頁面
- 頁面拿掉一個欄位，函式要跟著拿掉
- `tests/db/shares.test.mjs` 比對函式實際回傳的 key 與 `utils/share.ts` 的 `SHARED_BREW_KEYS`，`tests/unit/share-wiring.test.mjs` 確認分享頁用到其中每一個

| 群組 | 回傳的 key | 分享頁上顯示成 |
|---|---|---|
| 豆子 | `bean.name`、`bean.roaster`、`bean.roast_level`、`bean.roast_date` | 豆名（標題）、咖啡店名、烘焙度、烘焙日期；養豆天數由烘焙日期與沖煮日期即時算 |
| 參數 | `brewed_at`、`dose`、`water_temp`、`grind_setting`、`total_time`、`method` | 沖煮日期、粉重、水溫、研磨刻度、沖煮時間、沖煮手法。總水量與粉水比由分段即時算 |
| 器材 | `grinder`、`dripper`、`kettle` | 顯示名稱，已經組好（型錄的「品牌 · 型號 版本」，或自建名稱）。組法與 `utils/equipment.ts` 的 `catalogDisplayName` 相同，測試比對兩邊 |
| 分段 | `steps[]`：`step_index`、`step_type`、`cumulative_water`、`hold_seconds`、`note` | 段名（悶蒸、第 N 段）、攪拌標記、累積水量、停水時間、段落備註 |
| 品飲 | `rating`、`is_favorite`、`intensity`（只有四個已知的 key）、`flavor_tags`（名稱陣列）、`tasting_notes`（依設定） | 星等、收藏、強度、風味、心得 |
| 分享本身 | `is_owner`；本人時多一個 `brew_id` | 本人橫幅與「前往紀錄」 |

**不回傳**：`user_id`、email、任何 uuid（`bean_id`、器材 id、`share_id`）、`include_notes`、`is_sample`、`copied_from_brew_id` 與差異、三個耗時欄位、`created_at`／`updated_at`／`visibility`，以及濾紙、分享壺與 V2 的進階欄位（詳情頁不顯示，分享頁也不顯示）。

- **不回傳 id**，是為了讓分享頁上沒有任何可以拿去查別的東西的把手。
  **本人是唯一的例外**：`is_owner` 為 true 時額外回傳 `brew_id`，「前往紀錄」需要它；本人反正讀得到那筆紀錄。
- **不回傳 `include_notes`**：畫面不顯示它，心得在不在回傳值裡已經表達了一切（見下一條）。
- **研磨刻度一定連磨豆機的顯示名稱一起回傳。** 刻度 20 在不同磨豆機上是完全不同的粗細，單獨給一個數字等於給了一個會誤導的數字。磨豆機沒填時，刻度也不回傳。
- **心得筆記在函式裡就依 `include_notes` 決定回不回傳。** 不是回傳之後在畫面上藏起來——畫面上藏的話，開一下開發者工具就看得到，等於沒有這個設定。沒勾、或紀錄沒有心得時，**連 key 都不出現**。
- 其他沒有值的欄位回傳 `null`（key 在，值是 null），分享頁照詳情頁的規則不顯示那一列。
- `is_owner` ＝ `auth.uid() = brew_shares.user_id`。未登入時 `auth.uid()` 是 NULL，結果是 false。

**找不到就是找不到。** 代碼不存在、對應的紀錄已刪除（cascade 之後連 `brew_shares` 那一列都沒了），一律回傳 NULL，不分原因、不附說明。分原因等於告訴逐一試代碼的人「這一個曾經存在」。函式也照樣檢查 `revoked_at is null`——這一版不會有非 null 的列，但日後加回停止分享時讀取端不必再改。

**開啟事件由這支函式自己寫**（`viewer` 依 `auth.uid()` 判斷），一次開啟一列。前端不得另外呼叫一次，否則每開一次會記兩列。

### 14.3 寫入：也只走函式

`brew_shares` 與 `brew_share_events` **不給任何角色 insert／update／delete 的 table privilege**。兩個動作各一支 `security definer` 函式：

| 函式 | 回傳 | 做什麼 |
|---|---|---|
| `create_brew_share(p_brew_id uuid, p_code text, p_include_notes boolean)` | `text`（代碼） | 已有生效中的連結 → 直接回傳**現有**代碼，**不寫事件、不改 `include_notes`**；沒有 → 用 `p_code` 建一列並寫 `create` 事件 |
| `set_brew_share_notes(p_brew_id uuid, p_include boolean)` | `void` | 改生效中那一列的 `include_notes`；值真的變了才寫 `toggle_notes` 事件。沒有生效中的連結時 `raise exception` |

兩支都**先確認 `p_brew_id` 屬於 `auth.uid()`**，不屬於就 `raise exception`。不要靜默 return——靜默會讓前端以為成功，使用者拿到一個不存在的連結。

**`create_brew_share` 回傳的代碼可能不是送進去的那個**：同一筆紀錄已經在別的裝置分享過時，回傳的是既有的代碼。前端要比對，不一樣時代表剛才送出去的連結不會動（《02》§7.1）。

**`grant execute` 只給 `authenticated`，而且要先 `revoke`。**

```sql
revoke all on function public.create_brew_share(uuid, text, boolean) from public, anon, authenticated;
grant execute on function public.create_brew_share(uuid, text, boolean) to authenticated;
```

`20260831170000_grants.sql` 有 `alter default privileges … grant all on routines to anon, authenticated`，**新建立的函式會自動被授予 `anon` 執行權**。`security definer` 的函式被 `anon` 執行到，等於把一支繞過 RLS 的程式交給未登入的人——擁有者檢查會擋住它，但「擋得住」與「碰不到」是兩件事。寫 migration 時**每一支新函式都要明確 revoke 再 grant**，不要依賴函式內部的檢查當作唯一的防線。新函式也要加進 `tests/db/function-grants.test.mjs` 的 `ALLOWED` 與 `supabase/queries/函式權限盤點.sql` 的兩份清單。

**代碼由用戶端產生。** 理由在《02》§7.1：iOS Safari 的系統分享必須在點擊的同一個事件裡同步呼叫，等不了一趟網路請求。函式對代碼只做兩件事——格式檢查（`check` 約束）與唯一性（unique 約束）。使用者只能替自己的紀錄指定代碼，選一個爛代碼只傷得到他自己，所以這不是跨使用者的風險；**跨使用者的那一層是 `p_brew_id` 的擁有者檢查**，那一條不能省。

### 14.4 RLS 與 privilege

| 表 | policy | table privilege |
|---|---|---|
| `brew_shares` | 只有一條 select：`auth.uid() = user_id` | `authenticated` 只有 `select`；`anon` 沒有 |
| `brew_share_events` | 一條都沒有 | 兩個角色都沒有 |

`brew_shares` 保留 select，是因為紀錄詳情頁要知道「這筆分享了沒、目前勾了沒」，那是本人讀自己的列。`brew_share_events` 介面完全不讀，盤點在 SQL Editor 做，所以連 policy 都不寫——沒有 policy 又沒有 privilege 的表，`security definer` 函式以外碰不到。

兩張表都要在自己的 migration 裡明確 `revoke all … from anon, authenticated` 再把該給的 `grant` 回去，理由同 §9.2（`alter default privileges` 會先 `grant all`）。

**既有的五張表也要對 `anon` 收回。** `20260831170000_grants.sql` 當初對 public schema 的所有表 `grant all … to anon`（平台慣例，把關交給 RLS），所以匿名 `select brews` 拿到的是「0 列」而不是 permission denied。分享讓未登入的人第一次有了進到這個產品的正當理由，`brews`、`brew_steps`、`beans`、`user_equipment`、`brew_flavor_tags` 的防線不該只剩 RLS 一層：分享的 migration 一併 `revoke all … from anon`。`authenticated` 的權限不動；查表類的系統表不在這一輪的範圍。

**`brews` 的 RLS 一個字都不動。** 分享不經過 `brews` 的 policy，也不改 `visibility`（§3.5）。

### 14.5 照片

第一版的分享頁不顯示任何照片：紀錄詳情頁本來就不顯示豆袋照片，`brews.brew_photo_path` 是 V2。所以 `get_shared_brew` 目前不回傳照片欄位。

**之後要顯示時的規則先寫在這裡**：`bean-photos` 與 `brew-photos` 都是 private bucket，policy 以路徑第一層的 `auth.uid()` 判斷擁有者，匿名的人沒有權限。因此

- 不得把 `photo_path` 回傳給前端、讓它自己去要簽名網址
- 由 `get_shared_brew` 產生有時效的網址一起回傳
- **每次開啟重新產生，不快取、不寫進資料表。** 簽名網址是短期憑證，存下來等於把 private bucket 變成公開的
