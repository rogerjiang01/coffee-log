**2. 影響範圍**

- 只動 `brew_steps` 一張表，而且只動**含有攪拌段的那些紀錄**的列；沒有攪拌段的紀錄一列都不碰（本機驗過）

  併完之後的最後一段 `hold_seconds` 是 NULL（既有規則）。**總水量不變**

  任何一項不過就 `raise exception`，交易回復，資料維持原樣

**3. 備份**：見下面「備份的查詢」，在 SQL Editor 執行、把結果存成檔案。這台機器沒有 Docker，`supabase db dump` 跑不起來。

#### 草稿

```sql
do $$
declare
  b record;
  s record;
  n int;                    -- 已經留下來的段數（也是下一個要給的 step_index − 1）
  target uuid;              -- 目前併入的對象：上一個留下來的段
  target_hold int;
  target_notes text[];
  water numeric;            -- 上一個留下來的段的累積水量
  lead_id uuid;             -- 開頭的攪拌段裡的第一列：整組只有攪拌段時留它
  lead_hold int;
  lead_notes text[];
  has_lead boolean;
  note_part text;
  bad int;
begin
  create temp table stir_cleanup_before on commit drop as
    select brew_id, max(cumulative_water) as total_water, count(*) filter (where step_type <> 'stir') as other_steps
    from brew_steps
    where brew_id in (select brew_id from brew_steps where step_type = 'stir')
    group by brew_id;

  for b in select brew_id from stir_cleanup_before loop
    n := 0; target := null; target_hold := null; target_notes := '{}'; water := 0;
    lead_id := null; lead_hold := null; lead_notes := '{}'; has_lead := false;

    for s in
      select id, step_index, step_type, cumulative_water, hold_seconds, nullif(btrim(coalesce(note, '')), '') as note
      from brew_steps where brew_id = b.brew_id order by step_index
    loop
      if s.step_type = 'stir' and not (s.cumulative_water > water) then
        -- 攪拌段沒有注水：併掉。停水時長相加（兩邊都沒記才是 NULL），備註補「攪拌」（連續時只寫一次）
        if target is not null then
          if s.hold_seconds is not null then target_hold := coalesce(target_hold, 0) + s.hold_seconds; end if;
          if coalesce(target_notes[array_upper(target_notes, 1)], '') <> '攪拌' then target_notes := target_notes || '攪拌'::text; end if;
          if s.note is not null then target_notes := target_notes || s.note; end if;
          delete from brew_steps where id = s.id;
        else
          -- 開頭的攪拌段：等下一段出現再併進去
          if s.hold_seconds is not null then lead_hold := coalesce(lead_hold, 0) + s.hold_seconds; end if;
          if coalesce(lead_notes[array_upper(lead_notes, 1)], '') <> '攪拌' then lead_notes := lead_notes || '攪拌'::text; end if;
          if s.note is not null then lead_notes := lead_notes || s.note; end if;
          if has_lead then delete from brew_steps where id = s.id; else lead_id := s.id; has_lead := true; end if;
        end if;
      else
        -- 留下來的段。先把上一個對象寫回去
        if target is not null then
          update brew_steps set hold_seconds = target_hold, note = nullif(array_to_string(target_notes, '，'), '') where id = target;
        end if;
        if has_lead then delete from brew_steps where id = lead_id; end if;
        n := n + 1;
        target := s.id;
        target_hold := case when s.hold_seconds is null and lead_hold is null then null else coalesce(s.hold_seconds, 0) + coalesce(lead_hold, 0) end;
        target_notes := lead_notes;
        -- 攪拌段的累積水量比前一段多：其實注了水，留成一般段，備註前面補「攪拌」
        if s.step_type = 'stir' then target_notes := target_notes || '攪拌'::text; end if;
        if s.note is not null then target_notes := target_notes || s.note; end if;
        update brew_steps
          set step_index = n, step_type = case when s.step_type = 'stir' then 'pour' else s.step_type end
          where id = s.id;
        water := s.cumulative_water;
        lead_id := null; lead_hold := null; lead_notes := '{}'; has_lead := false;
      end if;
    end loop;

    if target is not null then
      -- 最後一個對象：它是最後一段，不存停水時長（既有規則）
      update brew_steps set hold_seconds = null, note = nullif(array_to_string(target_notes, '，'), '') where id = target;
    elsif has_lead then
      -- 整組只有攪拌段：留一段一般段，備註「攪拌」
      update brew_steps
        set step_index = 1, step_type = 'pour', hold_seconds = null, note = nullif(array_to_string(lead_notes, '，'), '')
        where id = lead_id;
    end if;
  end loop;

  -- 驗證：對不上就整支中止（交易回復，資料不變）
  select count(*) into bad from brew_steps where step_type = 'stir';
  if bad > 0 then raise exception '攪拌清理：還有 % 列 stir', bad; end if;

  select count(*) into bad
  from stir_cleanup_before before
  left join (
    select brew_id, max(cumulative_water) as total_water, count(*) as steps, max(step_index) as last_index, min(step_index) as first_index
    from brew_steps group by brew_id
  ) after using (brew_id)
  where after.brew_id is null
     or after.total_water is distinct from before.total_water       -- 總水量不能變
     or after.steps <> after.last_index or after.first_index <> 1   -- step_index 從 1 連續
     or after.steps < greatest(before.other_steps, 1);              -- 非攪拌的段一段都不能少
  if bad > 0 then raise exception '攪拌清理：% 筆紀錄搬移後對不上', bad; end if;

  select count(*) into bad
  from brew_steps last_step
  where last_step.hold_seconds is not null
    and last_step.step_index = (select max(t.step_index) from brew_steps t where t.brew_id = last_step.brew_id)
    and last_step.brew_id in (select brew_id from stir_cleanup_before);
  if bad > 0 then raise exception '攪拌清理：% 筆紀錄的最後一段還有停水時長', bad; end if;
end $$;
```

#### 先算有幾筆（推之前，SQL Editor）

#### 備份的查詢（推之前，SQL Editor；把結果的 `statement` 欄整欄存成 `.sql` 檔）

它只列會被動到的紀錄的分段，直接產生還原用的語句：先刪掉那些紀錄現在的分段，再照原樣寫回（連 `id` 一起）。

```sql
with affected as (
  select distinct brew_id from brew_steps where step_type = 'stir'
)
select statement from (
  select 0 as part, null::uuid as brew_id, 0 as step_index,
         '-- 攪拌清理前的備份。還原：整段貼進 SQL Editor 執行（先刪掉這些紀錄現在的分段，再照原樣寫回）' as statement
  union all
  select 1, null, 0, 'begin;'
  union all
  select 2, null, 0,
         format('delete from brew_steps where brew_id in (%s);',
                coalesce((select string_agg(quote_literal(brew_id), ', ') from affected), 'null'))
  union all
  select 3, s.brew_id, s.step_index,
         format('insert into brew_steps (id, brew_id, user_id, step_index, cumulative_water, hold_seconds, step_type, temp_override, pour_pattern, note) values (%L, %L, %L, %s, %s, %s, %L, %s, %L, %L);',
                s.id, s.brew_id, s.user_id, s.step_index, s.cumulative_water,
                coalesce(s.hold_seconds::text, 'null'), s.step_type,
                coalesce(s.temp_override::text, 'null'), s.pour_pattern, s.note)
  from brew_steps s join affected using (brew_id)
  union all
  select 4, null, 0, 'commit;'
) lines
order by part, brew_id, step_index;
```

- 先確認欄位沒有變（這段查詢寫死了十個欄位；多了欄位要補進去，否則還原會少資料）：

  ```sql
  select column_name from information_schema.columns
  where table_schema = 'public' and table_name = 'brew_steps' order by ordinal_position;
  ```

  預期：`id, brew_id, user_id, step_index, cumulative_water, step_type, temp_override, pour_pattern, note, hold_seconds`
- 存檔之後打開看一眼：第一行是註解、接著 `begin;`、一行 `delete`、每個分段一行 `insert`、最後 `commit;`。`insert` 的行數要等於上面「原始的列」的列數
- **還原只在清理之後、而且那些紀錄沒有再被編輯過時是安全的**：還原會把那幾筆紀錄的分段整組換回備份當時的樣子，之後在介面上改過的分段會被蓋掉

#### 套用後的驗證查詢（推之後，SQL Editor；**必須是 0 列**）

```sql
select '還有 stir 的列' as problem, count(*)::text as detail
from brew_steps where step_type = 'stir' having count(*) > 0
union all
select 'step_index 不是從 1 連續', brew_id::text
from brew_steps group by brew_id having min(step_index) <> 1 or max(step_index) <> count(*)
union all
select '最後一段還有停水時長', s.brew_id::text
from brew_steps s
where s.hold_seconds is not null
  and s.step_index = (select max(t.step_index) from brew_steps t where t.brew_id = s.brew_id)
  and s.note like '%攪拌%'
union all
select '有增量 0 的段（攪拌段沒有併掉）', s.brew_id::text
from brew_steps s join brew_steps prev on prev.brew_id = s.brew_id and prev.step_index = s.step_index - 1
where s.cumulative_water = prev.cumulative_water and s.note like '%攪拌%';
```

再用眼睛對兩三筆：打開備份檔裡的某一筆紀錄，在 app 的紀錄詳情看分段——**推之前和推之後畫面應該一模一樣**（推之前是程式在併，推之後是資料本來就長這樣）。這是最直接的檢查。

#### 重新加入的影響（iOS，2026-11-17 查證）

前提：**主畫面上的網頁 App 有自己的一份網站資料**（cookie、localStorage、IndexedDB），和 Safari 的不共用；**從主畫面移除圖示，那一份資料就一起刪掉**。
這個 App 的登入狀態存在 cookie（`@nuxtjs/supabase` 的 SSR cookie），沒存的暫存文字在 localStorage、暫存的豆袋照片在 IndexedDB——三樣都在那一份資料裡。

| 你的推測 | 成不成立 | 說明 |
|---|---|---|
| 要重新登入 | **大致成立** | 移除舊圖示＝登入的 cookie 一起刪掉。新圖示的資料是空的，**只有一個例外**：iOS 17.2 起，「加到主畫面」的當下會把 **Safari 裡**這個網站的 cookie 複製一次過去——所以如果那個人在 Safari 裡也登入著，新圖示打開就是已登入的。但一般人是在主畫面的 App 裡登入、Safari 裡沒有登入，所以**通知裡照「要重新登入」寫**比較不會讓人意外 |
| 沒存的暫存會不見 | **成立** | localStorage 與 IndexedDB 不會被複製（iOS 只複製 cookie），舊圖示的暫存隨著移除刪掉。**已經儲存的紀錄、豆子、器材、目標、設定都在資料庫，不受影響**（設定頁的分段時間開關存在 `profiles`，也不受影響） |
| （另外一項） | — | 記錄表單裡「濾紙與分享壺」那一區的展開狀態存在 localStorage，會回到預設的收合。不影響資料 |

**通知裡建議寫的三件事**（順序就是操作順序）：

1. **先把填到一半的表單存起來**（或確定不要了）：移除舊圖示時，沒存的內容會一起不見
2. 用 Safari 打開網址 → 分享 → 加入主畫面（新的圖示名稱是 Laeta），**再**把舊的「手沖咖啡紀錄」圖示移除。先加新的再刪舊的，中間不會沒有入口
3. 打開新的圖示，**重新登入一次**（記得帳號密碼；忘記密碼還沒有做，見 CLAUDE.md「暫緩」）

**查證的範圍與限制**：

- 「各自一份資料、移除就刪掉」：Apple 沒有正式文件寫明；依據是 WebKit 的 bug 討論（主畫面 App 不屬於 Safari、有自己的資料）與 OneSignal 的 iOS 文件（「移除圖示會刪掉那個網頁 App 的網站資料」）
- 「iOS 17.2 起複製 Safari 的 cookie」：WebKit 官方只寫了 macOS Sonoma 的 Dock 網頁 App 會複製 cookie、不複製其他資料；
  iOS 的對應工作（WebKit bug 257786）被移到 Apple 內部追蹤，沒有公開的 release note。iOS 17.2 這個版本只有第二手來源
- **兩項都沒有在實機上試過**。要確定的話：在一台 iPhone 上，舊圖示裡登入、在新增紀錄填一半不存 → Safari 裡**不**登入 → 加新圖示、刪舊圖示 → 打開新圖示，應該是登入頁；登入後打開新增紀錄，不會問要不要還原暫存
- 參考：WebKit「News from WWDC23」（webkit.org/blog/14205）、WebKit bug 257786、OneSignal「Web Push for iOS」（documentation.onesignal.com/docs/web-push-for-ios）

### 程式

**最快：Vercel 的 Instant Rollback。** 在 Deployments 找到上線前那一筆 Production 部署（commit `a2024f6`），選「Instant Rollback」（或「Promote to Production」）。
幾秒鐘生效、不用動 git，**首頁改版第一批與 Laeta 改版一起退掉**。缺點是 main 的內容和正式站不一致，之後要記得處理 git 這一邊，否則下一次 push main 又會把新版部署上去。

**git 這一邊：還原合併的 commit `456b4d4`。**

```bash
git checkout main
```

```bash
git revert -m 1 456b4d4
```

**⚠️ 這一步只退掉 Laeta 改版（redesign 的部分），首頁改版第一批還在**（2026-11-24 實際上線時發現的，在暫時的 worktree 裡驗過）。
原因：首頁改版第一批那 16 個 commit 在合併之前就已經在本機 main 上（沒推過），所以它們是合併的**第一個父 commit `1b72049`** 的一部分；
`-m 1` 的意思是「回到第一個父 commit」，退完的內容等於 `1b72049`，不等於上線前的 `a2024f6`。
那個狀態（只有首頁改版、沒有 Laeta）從 10 月之後就沒有人看過（第五節第 1 點），**要和 Instant Rollback 一致、整個退回上線前，再加一步**，
把首頁改版第一批那 16 個 commit 也還原成一個 commit：

```bash
git revert --no-commit a2024f6..1b72049
```

```bash
git commit -m "退回上線前（a2024f6）：還原首頁改版第一批"
```

```bash
git push origin main
```

- 兩步做完，main 的內容和 `a2024f6` 完全相同（2026-11-24 在暫時的 worktree 裡比過 tree，一致）。**一次上線是定案**（第五節），所以預設兩步都做
- 之後要再上線：**先還原那兩個還原**（`git revert <還原的 commit>`，新的先還原），再繼續改。直接再 merge 一次 redesign，git 會認為那些 commit 已經合併過、什麼都不帶
- 不要用 `git reset` 加 `push --force` 改 main 的歷史

**migration 不跟著程式退**（下一小節的表）。真的要還原 `sample_bean_name` 改掉的範例豆名，**只能用推之前存的備份 SQL**（第二節第 3 點「備份」那段查詢產生的 `update` 語句）：整段貼進 SQL Editor 執行。
遠端沒有復原點，備份是唯一的還原來源。`weekly_goals` 只新增一張表，退回程式時不要 drop（下表）。

### 資料庫要不要跟著處理

| 情況 | 資料庫 | 理由 |
|---|---|---|
| 退回程式，`weekly_goals` 已經推了 | **不用動** | 舊的程式不知道這張表、不會查它；表留著沒有影響。使用者設好的目標也留著，再上線時直接接上。不要 drop——那才是不可逆的 |
| 退回程式，攪拌清理**還沒做** | **不用動** | 舊的程式本來就認得 `stir`（有攪拌標記的介面） |
| 退回程式，攪拌清理**已經做了** | **不用動** | 清理後的資料就是一般的分段加備註，舊的程式照常讀寫。舊的介面會再讓人標攪拌段——那就等於清理要再做一次，所以建議清理排在新版穩定之後 |
| 攪拌清理本身搬錯了 | **用備份還原** | 把備份檔整段貼進 SQL Editor 執行。只在那些紀錄清理之後沒被編輯過時是安全的（第二節） |
| 退回程式，範例豆子的名稱已經改了 | **不用動** | 舊的程式照樣讀得到；畫面上會同時有「範例-」和「範例」標籤，重複但不會壞。不要為了這個把名稱改回去——那又是一次覆寫使用者資料 |
| 新版上線期間使用者存的資料 | **不用動** | 新版寫入的欄位和舊版完全相同（三批改版不改資料表；範例豆子的名稱是資料，不是欄位）。新版存的紀錄退回後照常顯示；唯一的差別是新版不會產生攪拌段 |

**退回之後使用者手上的暫存**：表單的自動暫存在瀏覽器的 localStorage，新舊版的格式相容與否沒有特別驗過。暫存 7 天自動失效，壞掉的暫存程式會自己丟掉（`utils/draft.ts`），最壞的情況是某個人填到一半的表單沒有被還原。
