# 手沖咖啡紀錄平台 — 功能規格

> 搭配《01-資料庫規格》使用。資料結構問題以該文件為準，本文件定義行為。

---

## 0. 給實作者的硬性約束

1. **不得新增本文件未定義的頁面或功能。** 有疑問就停下來詢問。
2. **不得實作第 10 節「明確不做」清單中的任何項目**，即使實作成本很低。
3. **表單自動暫存是必要功能，不是加分項。** 見第 6 節。
4. **必填欄位只有三個**：豆子的 `name`、沖煮紀錄的 `bean_id` 與 `dose`。不得對其他欄位加上必填驗證。

   `bean_id` 必填的理由：它在資料庫是 `not null`（《01-資料庫規格》§3.5），而這個約束是對的——一筆沖煮紀錄不掛在任何豆子上沒有意義，本產品的核心價值是「比較同一支豆子的不同沖法」，沒有豆子就沒有可比較的對象。

   前端必須自己擋下來。放行到資料庫才失敗，使用者看到的會是 Postgres 的原始錯誤。
5. **所有文案使用正體中文。** 語氣規則見《03-介面規範》第 5 節，該節依使用位置分層規定，不在此重複——同一條規則寫在兩處會產生無範圍的全域語氣指令，那正是把對話語氣套進按鈕與空狀態的來源。

## 1. 產品定位

一個給手沖咖啡愛好者記錄沖煮參數的工具。

**主要使用者**：已經有記錄習慣的人（目前用 Excel、Notion 或紙筆），痛點是記錄太慢、手機上難操作、記了之後難以回頭比較。

**次要使用者**：想開始記錄但不知從何下手的人。透過低門檻的首次流程與內建的手法、風味詞彙接住他們，但不為此犧牲主要使用者的體驗。

**核心價值排序**（決定資源分配的依據）：

1. 記錄成本低到不構成負擔——這是門檻條件，不是價值主張
2. **看得出自己在進步**——這是核心。使用者要能比較同一支豆子的不同版本，看見自己調整的軌跡
3. 參考他人的參數——延伸價值，第一版完全不做

**第一版明確不做社群功能。** 空的按讚數、空的追蹤列表只會向新使用者證明「這裡沒人」，比沒有這些功能更傷。

## 2. 使用情境

**情境 A：沖煮後補記（主要，約八成）**
沖完一杯，坐下來，打開 app，記下這次的參數和喝起來如何。大部分情況是「跟上次差不多，改了一兩個地方」。

**情境 B：沖煮前查閱（次要）**
準備沖某支豆子，打開 app 看上次怎麼沖的、哪一次最好喝，記在腦中再去沖。

**不支援的情境：沖煮當下即時記錄。** 這是刻意的取捨。不做計時器、不做逐段即時記錄、不做智慧秤連動。介面不需要為單手濕手操作優化。

由情境 A 的「改了一兩個地方」推導出本產品最重要的一條結論：

> **「複製既有紀錄」的使用頻率高於「從空白新增」。**

所有介面決策都應優先服務複製流程。從空白新增只有在第一次記錄某支豆子時才會發生。

## 4. 首頁

**首頁不是「新增入口」，是「查閱起點」。** 兩種使用情境都是先看既有紀錄，不是從零開始填表。

### 版面結構

上下兩區，不做視角切換。切換器會把決策成本丟給使用者，而兩區並存已經同時滿足兩種需求。

**上區：沖煮中的豆子**

橫向可滑動的卡片列，只顯示 `is_finished = false` 的豆子，依 `created_at` 倒序。實際上通常只有一到三支。

每張卡片顯示：豆袋照片（無照片時見下）、豆名、養豆天數、沖煮次數、愛心次數。點擊進入該豆子的詳情頁。

**有照片與無照片的卡片必須等高。** 無照片時以烘焙度對應的底色色塊填充，上面疊豆名。混合高度會讓整列版面破碎。

若沒有任何未喝完的豆子，整個上區不顯示（不要顯示空狀態文案佔位）。

**下區：沖煮紀錄時間軸**

所有紀錄依 `brewed_at` 倒序，無限捲動或分頁皆可，每頁 20 筆。

每筆顯示：豆名、沖煮日期、粉重與粉水比、水溫、研磨刻度、愛心狀態。若該筆是複製而來且有差異，顯示極簡的差異提示（例如「刻度 22→20」），這是讓使用者一眼看見調整軌跡的地方。

### 全域新增按鈕

固定在畫面右下的浮動按鈕，點擊進入 `/brews/new`。

若目前只有一支未喝完的豆子，直接帶入該豆子（`?bean={id}`），少一步選擇。

## 5. 新增沖煮紀錄

三種進入方式，共用同一個表單元件，差別只在初始值：

| 進入方式 | 路由 | 初始值 |
|---|---|---|
| 從空白新增 | `/brews/new` | 帶入常用器材；豆子欄位空白 |
| 指定豆子新增 | `/brews/new?bean={id}` | 同上 ＋ 豆子已選定 |
| **複製既有紀錄** | `/brews/new?copy={id}` | **複製來源的所有參數與分段**，品飲欄位清空 |

### 複製流程的細節（最高頻路徑，優先做對）

複製時**帶入**：豆子、手法、粉重、水溫、磨豆機、刻度、濾杯、手沖壺、濾紙、分享壺、沖煮時間、完整分段（含段落備註與攪拌標記）。

**器材全部帶入，包含 L2 的濾紙與分享壺。** 下方的「清空」清單只涵蓋品飲，器材不是品飲。不帶入的話，複製出來的紀錄反而比從空白新增還少（後者至少會套用預設器材），那不是本節的意圖。

複製時**清空**：愛心、心得筆記、強度評分、風味標籤、沖煮照片。品飲是這一次的新體驗，不該繼承。

`copied_from_brew_id` 寫入來源 id。`brewed_at` 設為當下。

理想動線是：使用者從詳情頁點「照這次再沖一次」→ 表單已填好 → 改一兩個數字 → 填品飲 → 儲存。**全程應可在 60 秒內完成。**

### 表單欄位配置

**L1（預設顯示）與 L2（收合在「更多設定」內）** 的判斷原則：不是重要與否，而是**變動頻率**。重要但幾乎不變的欄位（例如濾紙）交給預設值處理，不佔版面。

#### 區塊一：豆子與手法

| 欄位 | 層級 | 行為 |
|---|---|---|
| 豆子 | L1 | 下拉選擇，未喝完的排前面。可直接新增豆子（見下） |
| 沖煮手法 | L1 | 選填。選定後帶入分段模板 |

**豆子欄位必須支援「就地新增」**：選單底部有「新增豆子」，點擊開啟精簡的新增豆子表單（只要豆名 ＋ 可選拍照），儲存後自動選定並回到沖煮表單。**不得跳離頁面導致已填內容遺失。**

**手法帶入分段的邏輯**：使用者選定手法後，依已填的粉重與手法的 `default_ratio` 算出總水量，再依 `step_template` 的比例換算成各段的累積水量，並原樣帶入模板的停水時間（`duration`，不受粉重影響所以不換算），寫入分段區。若粉重尚未填寫，則在粉重填寫後才帶入。偏好關閉時停水時間照樣寫入，只是不在表單上顯示（見區塊三）。

帶入後使用者可自由修改任何數值、增減段數，`brew_method_id` 保持不變。**不得在儲存時檢查分段是否符合模板。**

**粉重變動時整組重算，不保留手動改過的值。** 總水量由粉重決定，不重算等於留著舊粉重的分段。唯一的例外是使用者自己增減過段數——此時段數與模板對不上，結構已經與模板無關，整組不動。

這條規則刻意選擇了可預測性而非資料保全。曾經實作過逐段快照，只重算「沒被手動改過」的那幾段，撤掉了：使用者不記得自己改過哪幾格，也看不到系統記著什麼快照，所以每次改粉重的結果他都無法預測，實測起來時有時無。整組重算偶爾會蓋掉他的修改，但那是他能在腦中模擬的規則。

**只有使用者改了手法或粉重才重算；系統把值寫回表單時不重算。**

| 情境 | 分段 |
|---|---|
| 使用者換手法 | 套用新手法的模板（新增、複製、編輯都一樣） |
| 使用者改粉重（已選手法） | 依上面的規則整組重算——複製之後改粉重也一樣，那是使用者主動改參數 |
| 打開複製或編輯表單 | 不重算，分段就是來源紀錄的實際分段 |
| 暫存還原 | 不重算，分段就是暫存裡的分段 |
| 全部清除 | 不重算。那是還原，不是改參數：分段退回初始值（複製流程就是來源紀錄的實際分段），手法標籤保留 |

**未來若要重新引入部分保留機制，必須先解決「使用者能否預測結果」這個問題**——例如在被保留的段落上做視覺標記，讓「哪幾段不會被重算」是看得見的狀態而不是隱藏的記憶。沒有解決這一點就不要再做一次。

#### 區塊二：核心參數

| 欄位 | 層級 | 行為 |
|---|---|---|
| 粉重 | L1 | **唯一必填**，數字，單位 g |
| 水溫 | L1 | 數字，單位 °C |
| 磨豆機 | L1 | 帶入常用器材 |
| 研磨刻度 | L1 | 依磨豆機型錄調整輸入範圍與小數支援 |
| 濾杯 | L1 | 帶入常用器材 |
| 手沖壺 | L1 | 帶入常用器材 |
| 沖煮時間 | L1 | 分:秒 輸入 |
| 沖煮日期 | L1 | 預設當下，可修改（`brewed_at`，含時刻） |
| 濾紙 | L2 | |
| 分享壺 | L2 | |
| 水質、水 TDS、室溫、濕度 | L2 | 第一版可全部不露出 |

**研磨刻度的輸入行為**：
- 依型錄的 `grind_scale_min` / `grind_scale_max` 顯示範圍提示；`max` 為 null 時不做上限檢查
  - 範圍提示的文案：高於上限「超出磨豆機刻度範圍」，低於下限「低於磨豆機刻度範圍」
  - 位置在參考資訊那一行的後面（「刻度 1–8　最小間隔 0.5　超出磨豆機刻度範圍」），顏色 `--notice`，見《03》§4.1。**不寫成「這台的刻度到 8 為止」那種定義句**：使用者要知道的是這個數字有問題，機器的規格就寫在同一行的左邊
  - 同時超出範圍又不符最小間隔時，只顯示範圍提示。範圍是「你可能看錯行了」，間隔只是「這台停不到那個位置」，兩則一起出現只會讓他兩則都不讀
  - 提示一行放不下時整段換到下一行並貼齊左緣，不縮排——下方的型錄備註都貼齊左緣，只有提示縮排會像排版出錯
- 依 `grind_scale_increment` 決定精度：為 `1` 時只接受整數，為 `0.5` 或 `0.1` 時接受對應小數，為 `null` 時接受任意數值
  - 不符時顯示「不符最小間隔」，整數格機型也是同一句（間隔的數字已寫在同一行左邊）。位置與顏色與範圍提示相同：接在參考資訊那一行後面、`--notice`，不另起一行
- 有 `grind_scale_suggested_min` / `max` 時，在欄位旁顯示實用範圍提示（例如「手沖常用 6–30」）
- 有 `grind_scale_note` 時，顯示為輔助說明（例如「一圈 40 格」）
- 自建器材（無型錄資料）時，不做任何驗證，自由輸入

**所有刻度驗證都只是提示，不得阻擋儲存。** 使用者可能改裝機器、可能用型錄未涵蓋的方式讀數。擋住輸入的代價遠高於容忍異常值。

**這條已經被實機測試檢驗過，結論是維持現狀。** 測試者在一台刻度只到 40 的磨豆機上填了 87，沒有被任何東西攔下來。查過之後確認兩件事都是規格本來就寫的：型錄機型會顯示「這台的刻度到 40 為止」但不擋儲存，自建器材（無型錄資料）連範圍提示都沒有。

不改的理由是**型錄資料可能有誤、使用者可能改裝**，系統不該拿自己的資料去否定使用者手上那台機器的實際數值。這一點在自建器材上更明顯：使用者自己打的名字，系統對它一無所知，憑什麼說 87 不對。提示的角色是「你可能看錯行了」，不是「這個數字不合法」——所以它不得改用 `--danger`（見《03》§4.1）；紅色會讓人以為存不起來，而它存得起來。

提示的視覺權重在階段 10 調過一次：範圍提示從 `--text-muted` 改為 `--notice`（《03》§4.1 的三層），之後最小間隔提示也併到同一位置、同一顏色。理由不是「不擋就要更大聲」，而是它原本與「刻度 1–8」那種一直都在的參考資訊同色——參考資訊使用者看久了會自動略過，提示混在裡面等於不存在。

真正該修的是提示**該出現卻沒出現**的情況，那是 bug 不是規格問題。已知並修掉一個：器材管理頁與沖煮表單共用同一個快取 key 卻各查各的欄位，先開器材管理頁再去填表單時，刻度規格全部變成 `undefined`，型錄機型的提示整段消失。修法見 `utils/equipment.ts` 的單一查詢定義。

**粉水比即時顯示**：粉重與總水量都有值時，在粉重欄位旁即時顯示「1:15.0」。這是衍生值，不可編輯、不存入資料庫。

#### 區塊三：分段注水

這一區是本產品與競品最主要的差異，必須做得比其他區塊更用心。

**所有段落在同一份清單裡**，悶蒸沒有單獨的區塊。`step_type` 為 `bloom` 的那一段只有三處不同：標題顯示「悶蒸」、不可刪除、不可標攪拌。外觀與其他段落相同，不另用底色或分隔區分。資料層它是 `step_index = 1`、`step_type = 'bloom'` 的一般段落。

**不是每組分段都有悶蒸。** 四六法的第一注不是悶蒸（《01》§3.7），模板第一段是 `pour`，所以「悶蒸永遠單獨呈現在最上方」這個前提不成立。沒有悶蒸時第一段就是一般段落：標題「第 1 段」、可刪除、可標攪拌。段號一律從悶蒸之後的第一個一般段落數起，不用陣列位置（否則會出現「第 0 段」）。既有紀錄裡已存成 `bloom` 的四六法第一注不回頭改，照存下來的樣子顯示。

**每一段兩個輸入格**：

| 顯示 | 輸入 | 儲存 |
|---|---|---|
| 「注到 ___ g」 | 累積水量 | `cumulative_water` 直接存 |
| 「停留 ___ 秒」 | 停水時間（「記錄停水時間」開啟時才顯示；最後一段不顯示） | `hold_seconds` 直接存 |

**填什麼存什麼，沒有換算。** 累積水量直接輸入——使用者沖煮時看的是磅秤上的累積數字；停水時間同樣原樣存進 `hold_seconds`（《01》§3.6）。

##### 「停留」＝注完之後到下一注之前的停水時間

不含注水動作本身。第一段的停留欄位下方一行輔助說明「停水時間」（`--text-muted`），只寫這一次——每段意思相同。標籤維持「停留」，那是咖啡圈的通用說法。

**舊定義是錯的，這一版改掉。** 舊版的「停留」是「這段開始注水到下一段開始注水」的全部時間，含注水動作。兩位實機測試者都填不出來：

> 「有點不知道他在講什麼，我以為是下沖的時間」

> 被告知定義之後，仍然說「不知道怎麼填」

根因是那個欄位要求使用者提供一個**他不知道的數字**：要填出段落總歷時，他得記得注水花了幾秒。而注水速率依器材與個人手法而異，還有行動誤差（眼睛看到 8 秒、身體開始動作要 2 秒），是他無法預期的。咖啡老闆的訪談也印證：給水時間不能預期，停水時間可以預期，而他實際在調整的就是停水時間。

**不拆成「注水」與「停水」兩個欄位**：輸入成本會翻倍，而給水時間本身沒有記錄價值。同一把壺、同一個人的給水速率相對固定。

**為什麼不用累加時間（計時器上的絕對秒數）。** 那看似更好填——眼睛盯著磅秤就看得到——但它混合了使用者能控制的（停水）與不能控制的（注水速率），還原出來的時間軸不能拿來做決策：使用者不會因為「第三段在第 90 秒開始」而改變什麼。而且這個欄位已經藏在開關後面，服務的是明確想記時間的進階使用者；那個位置該給最有決策價值的定義，不是為了降低門檻而妥協的近似值。

停水時間還有一個實務優點：**不受粉重影響**。停 30 秒對 15g 與 25g 都是 30 秒，物理意義不變。所以手法模板的時間數值可移植，不需要跟著粉重換算。

**最後一段不顯示這個欄位，也不存**（`hold_seconds` 為 NULL）。最後一注之後沒有下一注，「停水」這件事不存在；剩下的只是等它滴完，那段時間 `total_time` 已經記了。舊版在那裡顯示「`total_time` 減去最後一段時間點」的反推值，測試者看到「停 106 秒」當場說「這邏輯錯了」。

##### 記錄停水時間（使用者偏好）

**預設關閉**，存在 `profiles.record_step_times`（《01》§3.1）。

- 關閉：分段區每段只有「注到 ___ g」，沒有時間欄位，也沒有「停留」的輔助說明
- 開啟：時間欄位照常出現

**主要入口在分段注水區的標題列右側**，文字連結：關閉時是「記錄停水時間」，開啟時是「不記停水時間」。點擊即時切換，時間欄位跟著出現或消失。開啟之後在分段區下方回饋一行「之後的紀錄都會有時間欄位」（`--text-muted`），只在該次切換後顯示，重新進入表單不再出現。

**這是唯一的入口，設定頁沒有第二個控制點。** 從沒進過設定頁的人不知道有這個功能，而真正需要它的進階使用者剛好也是不會去翻設定的人——他看到表單沒有時間欄位，會直接認為這個 app 不支援。第二是距離：想開啟的時刻就在填表當下，卻要中斷填表、跳到設定、開啟、再回來。

設定頁曾經放過同一個開關，理由是「有些人習慣去設定裡找東西」——那是猜測，不是理由；反過來問「使用者不在填表的時候，為什麼會想關掉時間欄位」，想不出這個情境。而同一個偏好兩個控制點的成本是真的：要同步、文案要一致、改行為要記得改兩次。

用文字連結而不是 toggle 的理由見《03》§4.4。這不違反「欄位的存在本身就是一種指令」（《03》§4.0）：**入口不是欄位**——空的輸入框在說「這裡該填東西」，一個連結在說「這裡有個功能，你可以用」。

**判斷依據：分段時間是進階參數，預設不顯示。** 空欄位會讓沒有記錄習慣的使用者產生義務感，試著填出一個憑感覺回想的數字——那種資料沒有價值，而且會污染比較資料：以為在比較兩次沖煮，其實在比較兩次回想。同時，真正需要記錄時間的人確實存在，而且對他們來說這是關鍵參數：訪談確認悶蒸差 5 秒、停水差 7 到 8 秒就喝得出來。所以由使用者明確宣告要不要用，而不是預設出現在每個人的表單上（《03》§4.0 第三點）。

**關閉不影響既有資料。** 開關只決定新增與編輯表單上顯不顯示時間欄位：

- 不刪除任何已記錄的時間。既有紀錄的詳情頁與比較表照常顯示時間
- 關閉後編輯一筆已有時間的紀錄，**時間照樣保留**：欄位不顯示，但仍在表單狀態裡，儲存時照樣原樣寫進 `hold_seconds`，不可因為欄位不顯示而被清空
- 手法模板帶入的時間**照樣寫進資料庫**，只是不在表單上顯示。模板的數值是有依據的，不是使用者憑感覺填的；之後若開啟開關，那些紀錄的時間是完整的

沒記錄時間的紀錄，`hold_seconds` 全部是 NULL。顯示與差異計算一律當成「沒記錄」（《01》§8）。

每列右側有刪除鈕，列表下方有「新增一段」。段數無上限。

**分段區旁即時顯示總水量**（等於最後一段的累積水量），供使用者確認。這是衍生值，不另設輸入欄位。

段落類型（悶蒸／注水／攪拌／等待）放 L2，預設為「注水」。第一版可只提供切換為「攪拌」的選項。

溫度覆寫、注水手法、段落備註三個欄位第一版不露出。

#### 區塊四：品飲

| 欄位 | 層級 | 行為 |
|---|---|---|
| 愛心 | L1 | 明顯的切換按鈕 |
| 強度評分 | L1 | 四行五點選擇器，見下 |
| 心得筆記 | L1 | 多行文字 |
| 風味標籤 | L2 | 從標籤庫多選，可自建 |
| 出杯重量、飲品 TDS、沖煮照片 | L2 | 第一版可不露出 |

**強度評分必須留在 L1，不得收合。**

四個維度：酸質、甜感、醇厚、苦味。各為 1–5 的五個圓點，直接點選，一次點擊完成。**不使用滑桿**（手機上難精準）、**不使用下拉選單**（需兩次操作）。

四個維度全部可留空，留空不阻擋儲存，不顯示任何提示。

**這四個維度只描述強度，不評價好壞。** 好壞交給愛心與心得筆記。介面文案要避免任何暗示「分數高比較好」的措辭——不使用「評分」「分數」這類字眼，用「強度」。

**風味標籤是給新手的詞彙教學。** 多數人不記錄風味不是因為懶，是因為缺乏描述詞彙。標籤庫應分組顯示（酸質／甜感／口感／風味／缺陷），並使用具體可感的詞（例如「豆漿般的黏稠」而非「body 高」）。

### 儲存後

導向該筆紀錄的詳情頁，不要回首頁。使用者剛記錄完，最可能想確認自己記了什麼。

跳轉時表單那一頁不留在 history 裡（取代，不是新增一筆）：儲存後按返回不會回到表單。規則見《03》§3「離開流程時，表單頁不留在 history 裡」。

送出時寫入 `form_duration_seconds`：這一筆的互動秒數，閒置超過 60 秒的間隔不計入，只在新增流程寫入（定義見《01》§9）。此值不在任何介面顯示。

**每次儲存（含編輯）都往 `brew_save_events` 寫一列**：入口、三個秒數、時間（《01》§9.2）。這一列在紀錄儲存成功之後才寫，寫不進去不影響儲存結果、不顯示錯誤、不重試。`brews` 上的三個欄位維持原樣，編輯時仍然不更新。

同時寫入 `params_duration_seconds` 與 `tasting_duration_seconds`：同一批互動間隔依當下操作的區段分開累計（《01》§9.1）。表單上的 `data-section` 標記決定歸屬——「器材」「沖煮」兩張卡片與豆子欄位是參數，「喝起來」卡片與收藏是品飲，沖煮日期兩者都不算。這兩個值同樣不在任何介面顯示，既有紀錄維持 NULL。

### 分段儲存失敗

紀錄與分段是兩次寫入，不在同一個交易裡，所以可能出現「紀錄寫進去了、分段沒有」。這時留在表單上，顯示「紀錄已儲存，分段儲存失敗。請再按一次儲存。」，新增頁與編輯頁同一句。

**再按一次儲存必須安全**（2026-09-24 決定）。看到錯誤之後再按一次儲存是最自然的動作，這一下不能製造重複的紀錄：

- **新增頁**：記住已經建立的那筆紀錄。再按儲存時改為更新那一筆、重寫它的分段，不再新增。只在建立時寫入的欄位（三個耗時、`copied_from_brew_id`）不被第二次蓋掉（`utils/brewSave.ts`，`tests/db/brew-save.test.mjs`）
- **編輯頁**：本來就是更新同一筆，分段先刪後寫；表單上的分段還在，再按一次就補上

紀錄與分段改成同一個交易寫入、編輯頁「舊分段已刪、新分段未寫入」的風險，記在 CLAUDE.md 的暫緩清單。

## 6. 表單自動暫存（必要功能）

**問題背景**：競品 Beanconqueror 的最大缺陷是填到一半按返回會全部消失。這是使用者只會遇到一次、然後再也不回來的錯誤。

**實作要求**：

- 新增與編輯表單的完整狀態即時寫入瀏覽器，欄位變動時觸發，可 debounce 500ms
  - 文字欄位寫入 `localStorage`
  - 豆袋照片（裁切、壓縮後的圖）寫入 IndexedDB，key 與文字暫存相同。文字暫存裡只留一個「有照片」的標記。照片選定、更換、移除時立刻寫入，不等 debounce
  - 「移除」也要記進文字暫存（`photoRemoved`）。編輯既有豆子時，已上傳的那張不在暫存裡；不記的話重新載入後舊照片會回來、儲存時也不會刪——使用者以為移除了，實際上沒有。還原時維持移除後的樣子
  - 裁切畫面上還沒按「確認裁切」的原圖不暫存——只存裁切後的圖，與上傳一致（§9）
- **暫存依使用者隔離**：實際存放的 key 在 `draft:` 之後插入使用者 id，例如 `draft:{user_id}:brew:new`；IndexedDB 的照片用同一個 key。A 的暫存（含照片）B 根本讀不到，不靠任何清除動作——關分頁、session 過期、不登出直接換帳號都不會經過登出。也因此 B 不會看到拿 A 的暫存做參照檢查跳出的「上次選的照片沒能還原」「磨豆機已被刪除」。沒有使用者 id 時不暫存，不退回共用的 key
  改版前沒有使用者 id 的 key 不遷移：新程式不讀它們，由下方的過期掃描在 7 天後清掉，照片由 IndexedDB 自己的 7 天時效清掉
- 下列是表單用的邏輯 key，存放前都會加上使用者 id：`draft:brew:new`、`draft:brew:bean:{豆子 id}`、`draft:brew:copy:{來源 id}`、`draft:brew:{id}`、`draft:bean:new`、`draft:bean:{id}`、`draft:bean:inline`（沖煮表單裡就地新增的豆子）、`draft:equipment:new`、`draft:equipment:{id}`
- **新增沖煮紀錄的三種進入方式各自一個 key**：空白新增 `draft:brew:new`、指定豆子 `draft:brew:bean:{豆子 id}`、複製 `draft:brew:copy:{來源 id}`（同時帶兩者時以複製為準）。
  原本三者共用 `draft:brew:new`，結果是複製 A 的暫存被還原進複製 B 的表單——使用者拿到的不是他選的那一筆，而還原橫幅與「全部清除」出現在一張他剛選好來源的表單上，只是這個問題的症狀。進入方式本身就是使用者的選擇，暫存不能跨過它。指定豆子同理：帶不同豆子進來的暫存不該互相覆蓋。
  分開之後，同一個複製來源的暫存仍會還原、仍顯示橫幅（重整、切 app 回來都是真的中斷，要被保護）；那時按「全部清除」退回的是來源紀錄的參數與分段（§5 的重算規則）。
  複製與指定豆子的 key 會隨來源累積，改版前的舊格式 key 也不會再有人讀，所以開啟新增頁時主動清掉所有 `draft:` key 裡過期（超過 7 天）或壞掉的暫存，不分使用者、不分新舊格式。豆子表單的照片不在這裡清，IndexedDB 依自己的 7 天時效清。
- **沖煮表單的累計耗時跟著暫存走**：三個秒數（總、參數、品飲）與文字暫存同一個 key，還原時接著累積、不是從零開始。不存的話，iOS 回收分頁再打開之後那段時間會憑空消失，而耗時正是要用來驗證「記錄一兩分鐘內完成」的依據。存的是秒數不是時間點——中斷期間的間隔本來就不該計入，重新開始計時剛好是對的。暫存被清掉時（重新開始、全部清除、儲存成功）秒數跟著歸零。
  秒數不算「使用者填的內容」：判斷「與初始狀態相同嗎」時要排除它，否則打了字又刪回空白時會對著一張空表單顯示「未儲存的內容已恢復」
- 成功儲存後清除對應的暫存（文字與照片一起）
- 暫存超過 7 天自動失效（照片同樣 7 天）
- **登出時立即清除所有暫存**（隔離已經由上面的 key 保證，這是第二道防線）：`localStorage` 裡所有 `draft:` 開頭的 key 與 IndexedDB 裡的暫存照片，不看時效。與 7 天失效是兩回事——登出是使用者明確的動作；共用裝置上不清，下一個人登入會看到前一個人填到一半的內容。記憶體裡的查詢快取同時清空
- **查詢快取依使用者分區**：快取在記憶體裡、跨頁面存活，換帳號是站內跳轉、不重新載入。分區之後新使用者的格子是空的，第一個畫面一律未命中、走骨架，不會先閃過上一個帳號的畫面。分區用的使用者 id 先看 session（登入、登出當下同步更新），再看 claims（要晚一趟才換）。沒有使用者時整個快取停用

### 照片也要暫存

原本排除照片的理由是 Blob 放不進 `localStorage`，改用 IndexedDB 是另一個量級的工作。但當時沒考慮到一件事：**手機瀏覽器會自動回收背景分頁的記憶體**。使用者切去別的 app（去相簿找另一張、回一則訊息）再回來，頁面已經重新載入——那不是刻意的操作，而是最容易遺失資料的情境。

**判斷依據：分頁回收讓這個情境的發生率遠高於「使用者刻意重新整理」。** 刻意重新整理的人知道自己在做什麼；分頁被回收的人以為自己只是切了個 app。照片又是表單裡最難重來的東西——要重新找到那張、重新裁一次。

還原時照片讀不回來（被系統清掉、私密瀏覽）**不得讓表單壞掉**：其他欄位照常還原，照片欄位留空，並在欄位旁說明「上次選的照片沒能還原，請重新選一張」。

### 就地新增也要跨重新整理保留

沖煮表單裡就地新增的豆子，原本刻意只留在記憶體。那個設計假設「暫時離開」與「session 結束」是兩件事——但分頁回收讓這條界線消失了：使用者以為自己只是切了個 app，系統卻當成重新開始。

結果是最糟的組合：沖煮表單會還原，建到一半的豆子卻消失。使用者回來看到參數都在、只有豆子那格空了，而他可能不記得剛才填了什麼。

因此就地新增的豆子與豆子表單一致：豆名寫入 `localStorage`、照片寫入 IndexedDB（`draft:bean:inline`），7 天時效，按「取消」與儲存成功時刪除。「取消」與「關閉」的區分不變：關閉（返回、Esc、點外面）保留，取消清除。

### 還原分兩種，依離開多久決定

技術上無法區分「重整」與「隔天回來」——兩者對頁面都只是重新載入。但可以用**離開多久**當作使用者意圖的代理指標：剛離開幾乎必然是意外中斷（重整、螢幕熄滅、切 app、接電話），隔很久才可能是「上次沒填完的舊東西」。

**分界為 30 分鐘**，涵蓋通勤、開會、小睡這類典型中斷。這個值寫成常數，日後可調整。

**短時間（30 分鐘內）：直接填入，不詢問。**

頂部顯示 sticky 橫幅「未儲存的內容已恢復」，附一個「全部清除」按鈕。橫幅不擋畫面——沒有東西需要使用者決定。「全部清除」是次要動作，不用強調色。按下儲存或全部清除之後橫幅消失。

**「全部清除」只在這個橫幅上**，表單裡沒有第二個清除入口。橫幅只在有恢復內容時出現、捲離頂部時淡出。

時機是分開的兩件事，所以不綁在一起：

- **還原**（全部清除）回答「我不要這些內容」。這個念頭發生在看到內容的當下——打開表單發現裡面有東西那一刻——所以在頂部，跟告知一起出現
- **暫存狀態**（暫存中／已暫存）回答「我填的東西安全嗎」。這個焦慮發生在按儲存之前，視線在底部，所以在儲存按鈕下方（《03》§4.11）

按鈕文案維持「全部清除」：使用者剛被告知「有一份暫存」，清除是準確的描述。

**不得自動捲動頁面。** 使用者原本在哪個位置是他的位置，強制移動會讓他失去方向感；sticky 橫幅已經解決可見性。

自動暫存在填入後**立刻恢復寫入**——內容已經在表單上，使用者繼續填的東西應該被保護。

**超過 30 分鐘：用 overlay 詢問，不直接填入。**

這時使用者很可能是要記新的一杯，直接填入舊資料會讓他得先刪一輪才能開始。overlay 會擋住畫面、強制回應，那正是「我不知道你要哪個」的正確表達。

標題是陳述句「上次的內容尚未儲存」，三張表單（沖煮、豆子、器材）與新增、編輯共用：標題說明狀況，按鈕說明動作。

按鈕配置：左為「重新開始」（次要），右為「繼續填寫」（強調色，主要動作）。

overlay 還開著時**不得寫入暫存**，否則空白的表單會立刻蓋掉那筆暫存。橫幅模式不受此限。

### 指向已刪除資料的處理

暫存裡有豆子、器材、手法、風味標籤的 id，那些東西可能在這幾天內被刪掉。還原前必須確認對象是否還在，已刪除的欄位留空並告知使用者哪幾格空了。不處理的話還原後看起來一切正常，一按儲存就撞外鍵。

**離開頁面前不需攔截確認。** 有自動暫存就不需要用對話框打斷使用者。

## 7. 沖煮紀錄詳情頁

顯示該筆紀錄的全部內容。版面順序建議：豆子與手法 → 核心參數 → 分段 → 品飲 → 差異。

**衍生值在此頁完整顯示**：養豆天數、粉水比、總水量、每段增量水量、每段停水時間。沒記錄分段時間的紀錄（`hold_seconds` 全為 NULL）不顯示停水時間；最後一段本來就沒有停留（《01》§8）。

### 相對上一版的差異（核心功能）

若 `copied_from_brew_id` 不為空，顯示一個差異區塊，列出相對來源紀錄改動了哪些欄位。

```
相對上一次
研磨刻度  22 → 20
水溫      92 → 90°C
```

**比對範圍**：粉重、水溫、研磨刻度、磨豆機、濾杯、手沖壺、手法、沖煮時間、分段結構（段數／各段累積水量／各段停水時間）。

**這個功能的意義**：使用者不需要多做任何事，只是照原本的動線複製、改數字、儲存，系統就在背後留下他的調整軌跡。累積下來，配合愛心標記，就能看出哪些調整方向是對的。這是本產品「幫助使用者進步」的核心機制。

差異為空（複製後完全沒改）時，不顯示此區塊。來源紀錄已被刪除時（`copied_from_brew_id` 為 null），不顯示。

### 主要行動

**「照這次再沖一次」** 是此頁最主要的按鈕，導向 `/brews/new?copy={id}`。這是本產品最高頻的操作，按鈕權重應高於編輯與刪除。

編輯、刪除放次要位置。刪除需二次確認。

**分享**是這一頁唯一放在標題列上的動作，用圖示不用文字（《03》§3 的圖示封閉清單、§4.13）。它不與「照這次再沖一次」「編輯」「刪除」並排：那三個都改動自己的資料，分享改的是「誰看得到」，是另一種性質的事。流程見 §7.1。

### 7.1 分享一筆紀錄

使用者一鍵把一筆沖煮紀錄分享給朋友。朋友不論有沒有登入都能看，**只能看、不能改**；看的人不留副本，要再看就再點一次連結。

**入口**：紀錄詳情頁標題列（豆名那一行）最右端的分享圖示。只有本人看得到——別人本來就打不開這一頁。

#### 傳送模型（2026-09-23 決定）

**分享的本質是傳送**，像 LINE 傳出去的訊息，不是 Google 文件那種需要管理權限的共用。送出就是送出，沒有回頭修改——這和「不做停止分享」是同一個決定。

- **每次分享都產生一條新連結。** 同一筆紀錄分享三次，就是三條各自獨立的連結
- **設定跟著那一次傳送固定。**「分享心得筆記」勾了沒，在建立那一刻決定，之後不能改（《01》§14）
- **沒有「已分享過」的狀態。** 對話框不查、也不顯示這筆紀錄分享過沒有，永遠只有一種樣子

為什麼不重複使用同一條連結：重複使用唯一的價值，是之後管理時能一次切斷所有收到的人——我們不做管理，換不到這個好處。成本卻是實在的：連結代碼只能在手機上當場產生（見下方「iOS Safari 的限制」），要重複使用既有的連結就得在開啟對話框時先查詢，查詢還沒回來就按下分享的話，會撞上唯一限制而建立失敗。每次都產生新連結就沒有這個問題。

#### 分享對話框

按下圖示一律出現分享對話框。一般的置中對話框，樣式與刪除確認相同，結構是**標題 → 分享的對象 → 選項 → 動作**（版面見《03》§4.13.2）。

| 元素 | 內容 | 什麼時候出現 |
|---|---|---|
| 標題 | 分享紀錄 | 一律 |
| 分享的對象 | 左側：豆名，下一行「沖煮日期：09/20」。右側：這支豆子的照片。這是對話框的重點：讓使用者確認要送出去的是哪一筆 | 一律。**沒有照片就不放**，文字佔滿整個寬度 |
| 選項 | 小標「選項」＋勾選框「分享心得筆記」 | 這筆紀錄**有心得筆記**時。沒有心得時小標和勾選框都不出現 |
| 動作 | 支援系統分享：「複製連結」（次要）＋「分享」（主要）。不支援：只有「複製連結」一顆，是主要按鈕 | 一律 |

**按鈕依瀏覽器的能力決定**（有沒有 `navigator.share`），不依桌機或手機判斷。

**沒有「取消」或「完成」。** 關閉的方式是點遮罩或按返回鍵（《03》§3 的 history 行為）。

**「分享心得筆記」每次打開都預設不勾，不記住上次的選擇。** 兩種錯的代價不對等：不小心沒分享到心得只是少了一點資訊；不小心公開了私人心得就收不回來。

**用勾選框，不用開關。** 一般的規則是：立刻生效用開關，按確定才生效用勾選框。這個選項在按下「分享」或「複製連結」時才生效。

**不用網址參數控制是否顯示心得。** 收到的人自己改參數就能看到；心得回不回傳由讀取函式依那條連結建立時的設定決定（《01》§14.2）。

#### 按下按鈕之後

兩顆按鈕都是：**當場產生代碼 → 同步把連結交出去 → 關閉對話框 → 發出建立請求（不等待）**。

| 按鈕 | 交出連結的方式 | 回饋 |
|---|---|---|
| 分享 | 叫出系統分享選單（`navigator.share`） | 選單本身就是回饋，不另外顯示提示。使用者在選單裡取消**不算失敗**，不顯示任何訊息。系統分享在非取消的情況下失敗時，改成複製 |
| 複製連結 | 複製到剪貼簿 | 頁面底部顯示「已複製連結」，約兩秒後自己收起來 |

系統分享與複製都失敗時，頁面上顯示連結本身，附一行「無法複製，請長按連結手動複製」，使用者按「關閉」才收起。

#### iOS Safari 的限制決定了流程

**`navigator.share()` 必須在使用者點擊的同一個事件裡同步呼叫。** 中間只要先 `await` 一趟網路請求，Safari 就判定它不再屬於那個手勢而拒絕（`NotAllowedError`），使用者按了沒反應、也沒有錯誤訊息。寫到剪貼簿有同樣的限制。

所以**連結的代碼由用戶端當場產生**（`crypto.getRandomValues`，16 bytes 轉 base64url），網址在點擊的那一瞬間就已經是已知的，建立請求在交出連結之後才發、而且不等它。代碼的產生與驗證規則見《01》§14.3。

**這個順序的代價**：建立失敗時，連結已經送出去了，而它不會動。這是明講的取捨，處理方式是

- 對話框已經關了，所以失敗提示在**頁面層級**：「分享建立失敗，連結目前無法開啟」，附「再試一次」與「關閉」
- **這個提示不自動消失**，直到重送成功或使用者按「關閉」。連結已經傳出去了，失敗一定要被看到
- **「再試一次」用同一個代碼、同一個設定重送建立請求**，不再叫一次系統選單（連結已經送出去了）。成功之後，剛才送出去的那個連結就會開始生效。不重新產生代碼——重新產生會讓已經送出去的連結永遠是死的。資料庫對同一個代碼的重送是冪等的（《01》§14.3），第一次其實已經成功時也不會出錯
- 朋友在建立成功之前點開，看到的是「這筆分享已經無法查看」（§7.2）。這是對的：那一刻它確實不能看

#### 沒有「停止分享」

第一版不做停止分享（§11）。分享對話框、本人橫幅、紀錄詳情頁都不出現這個動作。

理由：心得筆記預設不分享，而且分享是傳送——送出就是送出，這和不能改設定是同一個決定。連結帶出去的除了心得，都是沖煮參數。這一版要切斷一個連結，方式是**刪除那筆紀錄**。

#### 埋點

記原始事件，怎麼解讀留到查詢時（同《01》§9.2 的原則）：**建立分享、開啟連結**。每一次傳送寫一筆建立事件，記下那一次「分享心得筆記」的設定。前一版的「切換包含心得筆記」事件不再產生，舊資料保留。

開啟事件記兩件事：開啟者**是否登入**、**是否為分享者本人**。**本人的開啟不得混進朋友的開啟次數**——分享者點自己的連結是常態（§7.2 的理由），不分開記的話，開啟數最大的貢獻者會是他自己。

欄位與寫入位置見《01》§14.1。**開啟事件由讀取函式自己寫**，前端不另外呼叫一次。

### 7.2 分享頁（`/s/[code]`）

**誰看得到**：任何拿到連結的人，不需要登入。頁面上沒有任何寫入的入口。

**看的人不留副本。** 不把這筆紀錄存進看的人的帳號、不提供「加到我的紀錄」。要再看就再點一次連結。

**內容 ＝ 紀錄詳情頁的內容，加上一小塊豆子資訊**（2026-09-23 決定）。順序與紀錄詳情頁一致（豆子與手法 → 核心參數 → 分段 → 品飲）。

- **多的那一塊豆子資訊**：咖啡店名、烘焙度、烘焙日期。本人從紀錄詳情點得進豆子詳情，這三項在那裡看得到；**朋友進不去豆子頁**，不補上的話他就少了判斷這杯咖啡的基本脈絡（哪裡買的、多深的焙度、烘好幾天了）
- **心得筆記依那條連結建立時的設定決定**（每條連結各自獨立，《01》§14）。沒勾時那一段整段不出現，不留「（沒有分享）」這類佔位——佔位等於告訴對方「這裡有東西你看不到」，比不提更刺眼
- **研磨刻度一定連磨豆機的型號一起顯示**（《01》§14.2）。刻度 20 在不同磨豆機上是完全不同的粗細
- 不顯示差異區塊、不顯示「範例」標籤、不顯示分享者是誰
- 沒有「照這次再沖一次」、沒有編輯、沒有刪除

**畫面上顯示的欄位與讀取函式回傳的欄位必須完全一致**（《01》§14.2）。回傳了卻沒顯示的欄位，開發者工具裡看得到，等於不知不覺多公開了資料。

**導覽**：**未登入的人不顯示分頁列**（他沒有可以去的地方，分頁列只會把他帶到登入頁）；**已登入的人顯示分頁列**。兩種都沒有 ‹——這一頁不屬於任何流程，對朋友來說也沒有上一層（《03》§3）。

#### 分享者本人打開時

頂端多一列**只有本人看得到**的橫幅：「你分享的紀錄」，旁邊只放「前往紀錄」。

理由：分享者點自己的連結，多半是想確認朋友看到什麼。所以橫幅以下的畫面與朋友看到的**完全一樣**——那正是他要確認的東西，本人版本不多顯示任何欄位（心得筆記沒勾時，本人在這裡也看不到）。

#### 失效畫面

紀錄已刪除、代碼不存在，**兩種情況顯示同一個畫面**，文案都是「這筆分享已經無法查看」，**不區分原因**。

分原因等於告訴逐一試代碼的人哪些代碼曾經存在。版面與按鈕見《03》§4.13。

## 8. 豆子詳情頁（核心價值落點）

除了豆子本身的資訊，此頁的重點是**該豆子所有沖煮紀錄的並排比較**。

### 比較表

一個橫向可捲動的表格。每一列是一次沖煮，欄位橫向對齊：

```
日期    養豆  粉重  粉水比  水溫  刻度  沖煮時間  ♥
03/12   12天  15g   1:15.0  92    22    2:30
03/14   14天  15g   1:15.0  92    20    2:20      ♥
03/15   15天  15g   1:16.0  90    20    2:25
```

依 `brewed_at` 排序（舊到新，看得出演變）。有愛心的列以底色標示。

**與前一列不同的數值要有視覺標記**（例如加粗或變色），這是讓使用者一眼看出自己改了什麼的關鍵。

點擊任一列進入該筆紀錄詳情。**可以點的線索是日期本身做成連結樣式**（`--accent`、底線）：日期是每一列的識別，使用者本來就靠它辨認「這是哪一次」，表格的識別欄做成連結是標準模式；日期欄是固定欄，橫向捲動時永遠看得到。整列仍然都可點，連結樣式只加在日期上。不另加 chevron（›）這類圖示。

**這張表是本產品對 Excel 使用者最實在的差異化。** Excel 在電腦上做得比這好，但在手機上做得極差——而喝咖啡的當下，人都在手機上。因此**這張表必須在手機上好用**：橫向捲動流暢、日期欄固定不動、字級足夠。

### 其他內容

豆袋照片、基本資訊、沖煮次數、愛心次數、養豆天數。

**主要按鈕只有一個，依這支豆子有沒有紀錄二選一，不並列：**

| 狀態 | 按鈕 | 導向 |
|---|---|---|
| 有紀錄 | 「照上次再沖一次」 | `/brews/new?copy={最新那筆的 id}` |
| 沒有紀錄 | 「用這支豆子沖一杯」 | `/brews/new?bean={id}` |

有紀錄時，按鈕下方用輔助文字（`--text-muted`）說明帶入哪一筆：「帶入 03/12 那次的參數」，日期格式與比較表相同。按鈕文字本身不塞這個資訊。

**為什麼不並列兩個按鈕**：實機測試時測試者找不到複製功能——他點「用這支豆子沖一杯」，看到空白表單，而複製藏在紀錄詳情頁。空白表單在這個產品裡幾乎沒有價值：想換手法、換粉重，複製之後改那幾格比從空白填快，而且複製會帶入上次的水溫、刻度、器材，那些多半不會變。並列兩個按鈕的成本不只是版面，是每次都要做一個沒必要的選擇。

**永遠複製最新那筆**（依 `brewed_at`，同時間再依 id），不做「有收藏就複製收藏的」這類規則。畫面上看不出來的規則違反可預測性——使用者無法從畫面判斷系統會帶什麼進來。想複製收藏那筆，從比較表點進那筆紀錄再複製。

已喝完的切換開關（影響首頁上區顯示）。

## 9. 首次使用流程

**這是整個產品風險最高的一段。** 日常流程可以在 60 秒內完成，但第一次使用要建豆子、建器材、填沖煮、填品飲，若不特別設計會超過五分鐘——比 Excel 還慢。而所有新使用者都從這條路徑進來。

### 新使用者一進來就有範例資料

註冊時自動建立三筆範例：一台磨豆機、一支豆子、一筆沖煮紀錄（內容與規則見《01》§13）。使用者第一次進來看到的是「記完之後長什麼樣子」，不是一片空白。

範例是他自己的資料：可以編輯、可以刪除、可以複製，行為與一般資料完全相同。列表卡片與詳情頁會多一個「範例」標籤（《03》§4.12），除此之外沒有任何差別。範例標記不因編輯而消失，也不會在刪除後重建。

**說明只有心得筆記裡的那一句**：這是範例、可以直接刪除、可以從豆子頁試一次複製。不做教學浮層、導覽步驟或其他說明文字——範例本身就是說明。

**既有使用者不補。**

### 設計原則

**每一步都可以跳過。** 使用者應該能在還沒建立任何器材的情況下完成第一筆紀錄。

**豆子只要豆名。** 建豆子表單的必填只有 `name`。其他欄位全部可空，不得加前端必填驗證。

**豆袋照片是逃生路徑。** 在建豆子表單的最上方放拍照／上傳，並以文案說明它是成本最低的記錄方式。這用極低成本讓不想打字的人也能完成，同時保留了資訊（人眼一秒就能從照片讀出產區處理法）。

**選了照片之後先裁切，再壓縮上傳。** 流程：拍照或選擇檔案 → 裁切 → 確認 → 壓縮 → 上傳。

- 裁切框固定為**正方形**，對應列表縮圖的比例——使用者在這一步就決定縮圖上會留下什麼，不必上傳之後才發現重點被切掉
- 框不動，照片在底下移動：單指拖曳平移、雙指縮放。**不做旋轉**
- **照片永遠不小於裁切框**（與 iOS 內建、Instagram 的裁切相同）：初始時照片短邊剛好等於框的邊長並置中——直式照片框貼左右、橫式貼上下；縮放縮到短邊等於框就停住，不回彈也不超過；拖曳到照片邊緣碰到框就停住。框內因此永遠不會出現空白或黑底
- 所有顯示豆袋照片的地方都是正方形容器（《03》§4.5），使用者在這一步框選的區域，就是之後每一處看到的區域
- **只存裁切後的圖**，不存原圖與裁切參數。豆袋照片的用途是辨識，使用者裁的時候本來就會把重要資訊框進去
- 裁切先於壓縮，壓縮流程不變（長邊 1600px、品質 0.8、轉 WebP、上限 2MB，見《01》§7）
- 裁切介面按取消：回到選照片之前的狀態，**不保留那張照片**。編輯既有豆子時按「換一張」再取消，原本那張照片留著——「不保留」指的是剛選的這張
- 豆子表單與沖煮表單裡的豆子就地新增兩處都有這一步（兩處共用同一個照片欄位）

實際措辭交給實作，本文件只規定意圖。逐字規定文案會讓規格與《03-介面規範》第 5 節的語氣分層打架。

**器材可以稍後再設定。** 第一次記錄時器材欄位允許留空。首筆紀錄儲存後，可以提示一次「設定常用器材，之後就會自動帶入」，但不強制、不阻擋。

### 空狀態

首頁在完全沒有資料時，不顯示空的兩區骨架，而是一個明確的行動引導。文案應說明第一步要做什麼，不要只寫「還沒有資料」。

空狀態是邀請行動的時機，不是說明現況的時機。

**有了範例資料之後，新使用者不會在第一次進來時看到空狀態**，但它仍然必要：使用者刪掉範例之後就會回到這個畫面，而那時他是刻意清空的，更需要知道下一步。

## 10. 查表型欄位的共通行為

適用於：處理法、品種、風味標籤、沖煮手法。

**產區不適用**——它是自由文字而非查表，理由見《01-資料庫規格》第 3.4 節。

**顯示規則**：系統內建項目排前面，使用者自建項目排後面，以視覺方式區分兩者。

**輸入行為是即時搜尋過濾，不是事後攔截。** 下拉本身可搜尋：

1. 點開選單就有搜尋框
2. 輸入時即時過濾現有項目，比對名稱與 `aliases`
3. 有相符項目直接列出讓他點
4. 打完字沒有完全相符的項目時，選單底部出現「新增『厭氧發酵』」
5. 點下去直接建立，不跳任何確認

減少同義異名重複（「厭氧」「厭氧發酵」「Anaerobic」變成三筆）的目的一樣達成——使用者打「厭氧」就會看到厭氧日曬與厭氧水洗，自然會選既有的。差別在於成本由系統承擔，而不是丟給使用者確認。

第一版不需要合併或管理介面。

**自建的項目只有本人看得到**（見資料庫規格第 6.3 節的 RLS policy）。

### 10.1 產國的例外

**產國適用「可搜尋 ＋ 分組顯示」，但不適用「新增『…』」。** `countries` 是純系統表（見《01-資料庫規格》§4.4），使用者不可新增，所以選單底部沒有建立那一列。

**分組依據是洲別（非洲／美洲／亞洲），不是系統／自建。** 產國沒有自建的概念，那個維度在這裡不存在。組內順序依台灣市場的常見度（存在 `sort_order`），不是字母序也不是 ISO 碼序——使用者不是在查字典，是在找他手上那包豆子。

搜尋時不分組，直接列出符合的結果：分組是給瀏覽用的，使用者已經打了字就代表他知道要什麼。

### 10.2 這一節的適用範圍怎麼判斷

**查表型欄位的共通行為由兩個維度決定，不是所有查表欄位都走同一套：**

| 維度 | 問題 | 影響 |
|---|---|---|
| 使用者能不能自建 | 這張表是混合表還是純系統表？ | 決定選單底部有沒有「新增『…』」 |
| 用什麼分組 | 這批項目對使用者而言的自然分類是什麼？ | 決定分組標題與排序依據 |

對照現況：

| 欄位 | 能自建 | 分組依據 |
|---|---|---|
| 處理法、品種、風味標籤、沖煮手法 | ✔ 混合表 | 系統內建／我建立的 |
| 產國 | ✘ 純系統表 | 洲別 |
| 產區 | — | 不適用，它是自由文字（見《01》§3.4） |

**新增查表型欄位時先回答這兩個問題，再決定沿用哪一套。** 預設把所有查表欄位做成同一個元件，會在「不能自建的表出現新增入口」或「分組維度不合使用者的心智」時出錯，而這兩種錯都不會報錯，只會讓人覺得哪裡怪怪的。


### 一條通則

**任何「提示確認」「你是不是」類型的互動，都要先問這個介面是在幫使用者還是在幫系統。**

若是後者，改成事前的過濾或引導，不要做成事後的攔截。

以本節為例：使用者當下的認知需求是「我要把這個記下來」，不是幫系統維護資料整潔。在他要建立新項目時擋住他問「你是不是指某某」，是把系統的顧慮轉嫁給他承擔。

## 11. 明確不做（V2 待辦）

以下項目已明確排除。**即使實作成本很低，也不得在第一版加入：**

- 社群功能：追蹤、按讚、留言、動態牆、公開瀏覽。
  **單筆紀錄的連結分享（§7.1、§7.2）不在此列**：沒有帳號關係、沒有動態牆、沒有任何人找得到別人的紀錄，拿到連結才看得到，而連結是猜不到的亂數。它是「把一杯咖啡傳給朋友看」，不是社群
- 預期參數與實際參數的雙軌記錄（第一版以自動差異替代）
- 注水手法細節：繞圈方向、繞圈半徑、水柱大小、繞圈速度
- 影片附檔
- 風味雷達圖
- 依熱門度排序的發現機制
- 豆袋 OCR 自動辨識（第一版僅存照片）
- 新手／進階的介面分流
- 沖煮計時器、智慧電子秤連動
- 跨磨豆機的刻度換算
- 資料匯出／匯入
- 第三方登入
- 深色模式（除非實作成本確實接近零）
- 多語系

**分享的第一版不做**（與上面同一條規則：即使成本很低也不做）：

- **分享頁的「用這組參數沖一杯」。** 它要求看的人先有帳號，而這個功能的前提是朋友不必登入；做成「先註冊再帶入」就變成招募流程，不是分享
- **LINE 的預覽卡**（Open Graph 圖與描述）。要做就得有一張伺服器端算繪的圖，而目前所有資料都在 `onMounted` 才查，等於要為這一件事加一條伺服器算繪的路徑
- **分享管理頁**（列出我分享過哪些、一次收回）。目前每一筆的狀態在它自己的詳情頁上看得到；要到「分享了很多筆、記不得有哪些」才需要一個清單，那時再做
- **停止分享**（2026-09-23 決定）。心得筆記每次預設不分享，而且分享是傳送：送出就是送出（§7.1 的傳送模型）；這一版要切斷一個連結，方式是刪除那筆紀錄。資料表保留了 `revoked_at`，日後加回時不必改表，但這一版沒有任何寫入它的路徑（《01》§14）

**注水手法細節特別說明**：這四個欄位在資料表上實作成本不高，很容易讓人覺得順手做一做。但它會讓分段區的每一段從兩個輸入變成六個，直接摧毀「一兩分鐘完成記錄」的目標。結構已預留，介面第一版不做。

## 12. 驗收標準

第一版完成的判斷依據：

1. 新使用者可以在五分鐘內完成註冊到第一筆紀錄，且過程中沒有任何強制步驟
2. 已有一筆紀錄的使用者，可以在 60 秒內透過複製完成第二筆
3. 表單填到一半離開再回來，內容還在
4. 豆子詳情頁的比較表在手機上可正常橫向捲動閱讀
5. 分段注水的「停留」是停水時間（注完到下一注之間），原樣存進 `hold_seconds`，最後一段為 NULL
6. 無段磨豆機（EK43）可以正常填寫刻度
7. 使用者 A 完全無法讀取使用者 B 的任何資料，包含自建的處理法與手法
8. `form_duration_seconds` 有正確寫入
9. 分享連結在 **LINE 的內建瀏覽器**裡實際開啟過，未登入、已登入、分享者本人三種身分各一次。
   LINE 的內建瀏覽器是這個功能實際的落地環境——連結多半從 LINE 傳出去、也從 LINE 點開——
   而它的 WebView 與 Safari／Chrome 行為不同（`navigator.share` 的支援、Cookie 的處理、
   「用外部瀏覽器開啟」按鈕的位置）。沒有在那裡開過，就不算完成
10. 《01》§14.6 的安全測試清單全部通過
